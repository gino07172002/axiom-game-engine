# R1 Authoring core and protocol — Codex review

## 摘要
交易核心在 SQLite transaction 內執行 revision 檢查，且 durable receipt 與修改原子提交，基本一致性設計完整。  
一般正確性仍有重要缺口：preview 可寫入、批次輸入可觸發 panic，以及 scenario 共用使用者存檔。  
AI 操作介面具備 selectors、投影與診斷，但 discovery schema、錯誤傳遞及 CLI 初始化存在落差。  
人類交接方面，純 ops 與相關 parity tests 有助維護；手寫 schema 與 Rust 型別已出現分歧。  
協作方面，import 缺少 CAS 入口，且 preview／proposal 的保護未涵蓋 undo。以下結論來自靜態閱讀，未執行測試或效能量測。

## Findings

### F1 [severity: high] [angle: collab] [confidence: high] ACL 的 undo 會繞過 preview 與 proposal，直接恢復世界
- 位置: `crates/axiom-core/src/acl.rs:925`、`crates/axiom-core/src/acl.rs:2339`、`crates/axiom-core/src/acl.rs:2825`
- 問題: `undo` 被歸類為 read statement，因此未經 preview／proposal 分支便直接提交。
- 證據: `is_edit()` 將 `Self::Undo(_)` 排除；read 分支直接呼叫 `read(store, stmt, expected_rev)`，沒有傳入 `preview` 或 `propose`；`Statement::Undo` 再執行 `Request::Undo`。後者於 `crates/axiom-core/src/store.rs:662` 插入 restoration revision。
- 影響: `axiom acl --preview -e "undo 1"` 仍會修改世界；`--propose` 也會跳過人類審核，直接撤回較新的編輯。
- 建議修正: 最小修正是在 read 分支明確拒絕帶有 `preview`／`propose` 的 `Undo`；補上兩種模式下 revision 不變的 regression tests。

### F2 [severity: high] [angle: code] [confidence: high] 批次中尚未驗證的 resource 可讓 selector panic
- 位置: `crates/axiom-core/src/local.rs:572`、`crates/axiom-core/src/protocol.rs:367`、`crates/axiom-core/src/store.rs:282`
- 問題: selector 假設 resource 內每個項目都有字串 ID，但同一批 edits 的中間狀態尚未經過驗證。
- 證據: `Store::edit_in` 套用全部 edits 後才在第 285 行呼叫 `compile()`；`set_where` 會先呼叫 `local::matches()`。其 widgets／rules 分支直接執行 `v["id"].as_str().unwrap()`；nodes／choices 也有相同假設。
- 影響: 一批請求先以 `set_resource` 放入 `ui.document = {"widgets":[{}]}`，再以 `set_where` 選取 widgets，即可在回傳 validation error 前 panic。CLI `serve` 會終止；live bridge 的處理執行緒也會退出。
- 建議修正: 將這些 `unwrap()` 改為附帶 resource、項目位置的 `Diagnostic`。補測 malformed intermediate resource，確認 apply／preview 回傳錯誤且不新增 revision。

### F3 [severity: high] [angle: code] [confidence: high] scenario 將測試 checkpoint 寫入共用遊戲存檔目錄
- 位置: `crates/axiom-cli/src/lib.rs:860`、`crates/axiom-cli/src/lib.rs:865`
- 問題: scenario 使用獨立 runtime，卻沒有隔離存檔。
- 證據: CLI 無條件呼叫 `run_with_saves(..., Some(db.parent().join("saves")))`。已追查其呼叫路徑：scenario 的 `Save` 會呼叫 `save_slot`，同名 slot 會替換原檔，後續再次寫入時還會移除舊 backup。
- 影響: 使用預設 `data/world.sqlite` 執行包含 `save` 的 scenario，會寫入 `data/saves`。即使使用 `data/qa.sqlite`，同世界 ID、同 slot 仍會與正式存檔碰撞。
- 建議修正: 預設使用記憶體 checkpoint，即傳入 `None`；需要驗證磁碟存檔時，要求明確的 `--save-dir` 或建立每次執行獨立的 QA 目錄。

### F4 [severity: high] [angle: code] [confidence: high] set_where 可將小型請求放大成數 GiB 的中間世界
- 位置: `crates/axiom-core/src/protocol.rs:365`、`crates/axiom-core/src/protocol.rs:382`、`crates/axiom-core/src/local.rs:122`、`crates/axiom-core/src/store.rs:285`
- 問題: request bytes 與 edit count 的限制沒有約束 selector 展開後的資料量；欄位驗證又延後到整批完成。
- 證據: `set_where` 最多接受 4096 個 targets，逐一 `value.clone()`；每次 `Target::edit` 都以 `json!(world)` 建立整份文件，再於 `local.rs:248` 反序列化整個 World。全部 targets 完成後才 `compile()`。
- 影響: 在合法的 4096-entity 世界上，將約 900 KiB 字串設到所有 `/label`，請求仍小於 1 MiB，卻會嘗試建立約 3.5 GiB 的 labels，最後才發現 label 超長；期間還反覆複製整個世界。這是配置量的靜態推算，未量測實際峰值或耗時。
- 建議修正: 展開前檢查欄位限制與累計寫入 byte budget，超額即回傳診斷；避免每個 target 都重新序列化整個 World。加入低預算的拒絕測試。

### F5 [severity: medium] [angle: code] [confidence: high] export 會把遠端錯誤當成成功並覆寫輸出檔
- 位置: `crates/axiom-cli/src/lib.rs:593`、`crates/axiom-cli/src/lib.rs:885`、`crates/axiom-cli/src/lib.rs:889`
- 問題: export 未確認遠端 response 成功，也未確認存在 `world`。
- 證據: dispatch 直接回傳 bridge 的 JSON Value；export 隨即將 `result["world"]` 寫檔，再自行建立 `{"ok":true,...}`。對錯誤 response 而言，缺少的 `world` 會變成 `null`。
- 影響: 例如連線模式下使用 `--request-id export-1 export backup.json`，Query 被包成 Execute，而 `store.rs:682` 只允許 Apply／Undo；遠端回傳錯誤後，CLI 仍會把 `backup.json` 覆寫為 `null` 並報成功。
- 建議修正: 在使用 response 前傳遞 `ok:false`；另要求 `world` 存在且能解析為 World，確認後才寫檔。補測遠端失敗時既有輸出檔保持不變。

### F6 [severity: medium] [angle: collab] [confidence: high] import 無法指定 expected_rev，會無條件取代最新世界
- 位置: `crates/axiom-cli/src/lib.rs:291`、`crates/axiom-cli/src/lib.rs:878`
- 問題: import 入口沒有 revision 衝突保護選項。
- 證據: `Command::Import` 只有 `file`，轉換為 Apply 時固定設定 `expected_rev: None`，edit 則是 `ReplaceWorld`。
- 影響: AI 匯出 revision N、修改檔案後，人類已在 GUI 提交 N+1；AI 執行 import 仍會成功覆蓋人類的修改。該子命令無法表達「僅在 N 仍為最新時匯入」。
- 建議修正: 為 import 加上 `--expected-rev` 並傳入 Apply；補上兩個連線間 stale import 被拒絕的測試。

### F7 [severity: medium] [angle: code] [confidence: high] serve 的 request 大小限制在整行配置完成後才生效
- 位置: `crates/axiom-cli/src/lib.rs:897`、`crates/axiom-core/src/protocol.rs:536`
- 問題: 持續服務入口的讀取本身沒有上限。
- 證據: `stdin().lock().lines()` 先建立完整 String，第 902 行才呼叫會檢查 1 MiB 限制的 `parse_request()`。
- 影響: 輸入端送出巨大單行或持續不送 newline，程序會在 parser 有機會回傳錯誤前持續配置記憶體。
- 建議修正: 使用有界的逐行 reader；超過 1 MiB 後丟棄到該行結束、回傳 compact error，並繼續處理下一行。測試超長行後仍能接受合法請求。

### F8 [severity: medium] [angle: ai] [confidence: high] discover typed 無法發現世界自訂的 component／resource schema
- 位置: `crates/axiom-core/src/registry.rs:712`、`crates/axiom-core/src/store.rs:343`
- 問題: typed discovery 沒有使用目前世界。
- 證據: Registry 固定呼叫 `typed_schema(self, &World::empty("discover"), id)`；Store 的 Discover 也只委派給 Registry。相對地，`typed_schema.rs:70` 明確支援從傳入 World 的 `component_schemas`／`resource_schemas` 查詢。
- 影響: 已成功定義並使用的自訂型別，透過 `discover typed:ID` 仍得到 unknown type；AI 必須另行讀取原始世界資料，才能理解作者新增的欄位。
- 建議修正: Store 對 `typed:` topic 傳入目前 World，Schema／Discover 共用此路徑；測試定義與修改自訂 schema 後的 discovery 內容及 hash。

### F9 [severity: medium] [angle: human] [confidence: high] 手寫 discovery schema 已與 Rust 協定型別分歧
- 位置: `crates/axiom-core/src/discovery.rs:34`、`crates/axiom-core/src/discovery.rs:59`、`crates/axiom-core/src/discovery.rs:77`
- 問題: 維護者必須同步修改多份定義，目前已有可確認的不一致。
- 證據: `set_where` 引用的 selection schema 將 `limit.maximum` 設為 128，實作卻允許 4096；gameplay action schema 沒有 `GameAction::Call`（`gameplay.rs:174`）；command schema 也沒有 `RuntimeCommand::Batch`／`Slide`（`gameplay.rs:264`、268）。
- 影響: 依 discovery 建立的驗證器會拒絕引擎實際支援的請求；新開發者只更新 enum 或執行邏輯，便可能留下無法由 AI 發現的功能。
- 建議修正: 先補齊缺少的 variants，將 read selection 與 edit selection 的限制分開；加入以各 variant 合法樣本驗證 discovery schema 的 parity tests。

### F10 [severity: medium] [angle: ai] [confidence: high] 本地查詢與 schema 指令會先載入無關的預設內容包
- 位置: `crates/axiom-cli/src/lib.rs:315`、`crates/axiom-cli/src/lib.rs:567`
- 問題: CLI 在分派 schema、query 等命令前，無條件計算 initial world。
- 證據: `Store::open_with(..., initial(...)?)` 會先求值；未指定 pack 時，`initial()` 只要發現 `content/fps/world.json`，就執行 `ContentPackage::load`。即使資料庫已存在、根本不需要 initial world，也會走此路徑。
- 影響: 預設 FPS 包損壞或缺少資產時，對另一份正常資料庫執行 query／history 也會失敗；連純 Registry 的 schema discovery 都受到內容檔案阻擋。
- 建議修正: 純 Registry 命令先行處理；Store 初始化改用 lazy initial factory，僅在空資料庫需要建立第一個 revision 時載入內容包。

### F11 [severity: low] [angle: collab] [confidence: high] Diff 的順序路徑會與合法的 order 物件 ID 碰撞
- 位置: `crates/axiom-core/src/diff.rs:102`、`crates/axiom-core/src/diff.rs:113`
- 問題: 物件與陣列順序共用 `/@order` 位址。
- 證據: keyed item 使用 `"{path}/@{ID}"`，order change 固定使用 `"{path}/@order"`；因此合法 entity ID `order` 與順序紀錄相同。merge 已於 `ops_merge.rs:73` 改用 `/entities#order` 避免此問題。
- 影響: 刪除名為 `order` 的 entity 時，同一 diff 會有兩筆相同 path，分別表示物件刪除與順序變化；以 path 索引的稽核工具會混淆兩者，且 diff 與 merge 的位址不一致。
- 建議修正: Diff 的順序標記改用不會與 ID 碰撞的 `#order`，並與 merge 統一；補測 entity ID 為 `order` 的新增、刪除及重新排序。
