# R7 Genre gameplay and game UI — Codex review

## 摘要

程式正確性：FPS 批次編輯與 RTS 共用導航可觸發 panic，RTS 資源交付可溢位，Action 在無敵人的共用戰鬥場景會誤判勝利。  
AI 可用性：CLI 已能操作多數玩法，但敘事分析、無變數滑桿與 Showcase 自動環繞的結果無法完整透過 CLI 驗證。  
人工交接：FPS 相容層重做了部分 v2 實體刪除邏輯，導致同一個刪除操作是否清理引用取決於入口。  
協作：交易支援 `expected_rev`，但 Showcase 拖曳草稿未綁定起始 revision，部分熱載入邏輯也會覆蓋已提交的內容變更。

## Findings

### F1 [severity: high] [angle: code] [confidence: high] FPS 批次編輯可在最終驗證前 panic

- 位置: `crates/axiom-fps/src/editing.rs:75`、`crates/axiom-fps/src/editing.rs:91`、`crates/axiom-fps/src/content.rs:253`
- 問題: 相容編輯直接以字串索引寫入可能已被同一批次改成非物件的 JSON 值。
- 證據: 通用 `set_component` 先寫入原始 `Value`，Store 執行完整批次後才編譯驗證。`from_world` 只按 `fps.sentinel` 鍵是否存在計數。接著 `enemies.speed` 或 `enemies.damage` 使用 `.entry("fps.sentinel".into()).or_insert_with(|| json!({}))[field] = value.clone()`。既有值為數字時，該索引會 panic。
- 影響: 同一個 `apply` 或 `preview` 先把 sentinel 元件設成數字，再做群組速度修改，請求會在產生結構化錯誤前中止。
- 建議修正: 用 `as_object_mut()` 檢查既有元件，以實體 ID 和元件路徑回傳錯誤。新增混合通用與相容編輯的批次測試，確認錯誤可恢復且 revision 不變。

### F2 [severity: high] [angle: code] [confidence: high] RTS 共用導航可因重複阻擋格而 panic

- 位置: `crates/axiom-rts/src/nav.rs:26`、`crates/axiom-rts/src/simulation.rs:1362`、`crates/axiom-runtime/src/rts.rs:589`
- 問題: 作者資料通過個別驗證後，合併共用戰鬥障礙仍可使阻擋清單超過上限。
- 證據: `Grid::new` 限制 `blocked.len() <= 16384`，同一座標出現多次仍會通過。`set_combat` 複製原清單，加入共用障礙覆蓋的其他格子，最後執行 `Grid::new(config).expect("validated shared navigation grid")`。
- 影響: 在合法的 `128 × 128` grid 中，原清單若含重複座標，共用障礙又涵蓋所有剩餘格子，合併結果會超限。首次固定步即可使遊戲中止。
- 建議修正: 用既有 grid 的格子遮罩合併阻擋，讓每格只占一個位置。於 runtime 準備階段建立共用 grid，透過 `Result` 回報建置失敗。

### F3 [severity: high] [angle: code] [confidence: high] RTS 礦物交付可使陣營餘額溢位

- 位置: `crates/axiom-rts/src/lib.rs:162`、`crates/axiom-rts/src/lib.rs:184`、`crates/axiom-rts/src/simulation.rs:141`、`crates/axiom-rts/src/simulation.rs:667`
- 問題: 驗證接受完整的 `u32` 起始餘額，交付時直接在同一型別上加總。
- 證據: `Session::validate` 檢查陣營與模擬預算，未檢查 `initial_balance` 加上可採資源的上限。交付執行 `self.balance[faction] += amount`，隨後將工人載量歸零。
- 影響: 餘額為 `u32::MAX` 的陣營收到一單位礦物時，debug 建置會 panic，預設 release 建置會回繞成零，破壞資源守恆。
- 建議修正: 在世界驗證時以 `u64` 計算並檢查每個陣營的最大可能餘額，將錯誤指向 `initial_balance`。加入上限交付的回歸測試。

### F4 [severity: high] [angle: code] [confidence: high] Action 在無敵人的共用戰鬥場景誤判勝利

- 位置: `crates/axiom-action/src/simulation.rs:172`、`crates/axiom-action/src/simulation.rs:317`、`crates/axiom-runtime/src/action.rs:190`、`crates/axiom-runtime/src/action.rs:275`
- 問題: 啟用共用戰鬥後，空的敵方集合會讓 `victory()` 回傳 `true`。
- 證據: 共用分支對敵方 bodies 執行 `.all(|b| !b.alive())`。獨立分支另有 `opponents.peek().is_some()`。`request` 在勝利時拒絕攻擊與閃避，`sync` 在第一次判定勝利時發布 `action.victory`。
- 影響: 只有英雄與友方的社交或探索世界，啟用 `combat.session` 後會發布勝利事件，攻擊與閃避也會收到 `round has ended`。
- 建議修正: 共用分支也要求至少存在一個敵方 body，再檢查是否全數死亡。測試有共用戰鬥但無敵人的場景。

### F5 [severity: medium] [angle: collab] [confidence: high] Showcase 滑桿可用舊草稿覆寫剛提交的 CLI 修改

- 位置: `crates/axiom-runtime/src/showcase.rs:533`、`crates/axiom-runtime/src/showcase.rs:539`、`crates/axiom-runtime/src/ui.rs:11`
- 問題: 拖曳草稿只保存數值。送出時使用放開滑桿那一幀的 `state.revision`。
- 證據: `numeric_drafts.entry(key.clone()).or_insert(stored)` 跨幀保留草稿。拖曳結束後，`Action::Apply` 把當下的 `state.revision` 放進 `expected_rev`。
- 影響: 人類在 revision 10 開始拖曳，AI 在期間修改同欄位，且 revision 11 已載入。人類放開滑桿時，舊草稿會以 revision 11 通過檢查，直接覆寫 AI 的修改。
- 建議修正: 草稿同時保存起始 revision，提交時使用該值。衝突時保留草稿並顯示最新欄位值。加入拖曳跨 revision 的 GUI 與交易測試。

### F6 [severity: medium] [angle: collab] [confidence: high] 敘事熱載入會掩蓋已提交的場景啟用修改

- 位置: `crates/axiom-runtime/src/gameplay.rs:102`、`crates/axiom-runtime/src/gameplay.rs:605`、`crates/axiom-runtime/src/gameplay.rs:759`
- 問題: 熱載入無條件沿用同 ID 場景的執行狀態，連作者明確修改的 `active` 也一併覆蓋。
- 證據: `Gameplay::new` 從 `w.scenes` 讀取 `active`。同一世界的 `transfer` 隨後以 `self.active[i] = old.active[j]` 覆寫所有配對場景，再呼叫 `sync_scenes()`。
- 影響: AI 或編輯器提交場景開關後，`query` 可看到新值，執行期也可到達新 revision，但 `observe` 的 `active_scenes` 與畫面仍保留原狀。
- 建議修正: 比對前後作者版本的場景旗標。作者值改變時採用新值，其餘場景沿用執行進度。測試提交、觀察與 undo 的完整路徑。

### F7 [severity: medium] [angle: collab] [confidence: high] 切換 FPS 世界會沿用前一個世界的戰局

- 位置: `crates/axiom-runtime/src/fps/mod.rs:155`、`crates/axiom-runtime/src/fps/simulation.rs:251`、`crates/axiom-runtime/src/fps/simulation.rs:267`
- 問題: FPS 的 `transfer` 未檢查來源與目標世界 ID。
- 證據: `transfer` 忽略 `_previous`，只要舊系統能轉成 `FpsSystem` 就呼叫 `restore_from`。後者移轉玩家血量、彈藥、擊殺與射擊統計，並依實體 ID 移轉 sentinel 狀態。
- 影響: 切換到另一個使用相同 sentinel ID 的 FPS 世界時，新地圖可能帶著舊地圖已死亡的敵人、剩餘彈藥與計分開始。
- 建議修正: 只在兩個 `compiled.source.id` 相同時移轉 FPS 狀態。加上不同世界共用實體 ID 的切換測試。

### F8 [severity: medium] [angle: collab] [confidence: high] RTS 熱載入新增礦點會破壞資源守恆

- 位置: `crates/axiom-rts/src/simulation.rs:236`、`crates/axiom-rts/src/simulation.rs:1530`、`crates/axiom-rts/src/simulation.rs:1610`、`crates/axiom-runtime/src/rts.rs:719`
- 問題: 新礦點保留新內容的存量，但守恆基準固定沿用舊世界的總量。
- 證據: 新 simulation 會初始化所有 `rts.resource`。`restore` 只覆寫同 ID 礦點的 `remaining`，再將 `initial_economy` 設為 `old.initial_economy`。`validate` 會將新礦點納入當前總量。
- 影響: 在進行中的同一世界新增有存量的礦點，熱載入後可採資源增加，RTS 驗證會回報 `resource conservation failed`。刪除仍有存量的礦點也會造成相反方向的差額。
- 建議修正: 依新增礦點的初始存量及刪除礦點的剩餘存量調整守恆基準，並在接受移轉前執行 `self.validate()`。測試新增與刪除各一例。

### F9 [severity: medium] [angle: code] [confidence: high] RTS 交付事件把同 tick 的生產支出扣掉

- 位置: `crates/axiom-runtime/src/rts.rs:592`、`crates/axiom-runtime/src/rts.rs:638`、`crates/axiom-rts/src/simulation.rs:669`、`crates/axiom-rts/src/simulation.rs:1347`
- 問題: `rts.delivered.amount` 使用陣營餘額的淨增量，可能低報或漏報實際交付。
- 證據: runtime 在 `sim.step` 前保存 `balance`，之後用 `saturating_sub(previous)` 計算事件金額。`Simulation::step` 先跑可呼叫 `train` 扣款的 `think()`，再跑入帳的 `decision()`。
- 影響: 對手同一 tick 排入生產並交付礦物時，只要支出等於或超過交付量，就不會發布該陣營的 `rts.delivered`。依此事件推進的行為規則會漏掉一次有效交付。
- 建議修正: 在實際交付處累加每個陣營本 tick 的交付量，runtime 用該數值發布事件。測試同一 tick 同時交付與生產扣款。

### F10 [severity: medium] [angle: code] [confidence: high] UI 圖片讀取缺少資產根目錄檢查及實際讀取上限

- 位置: `crates/axiom-runtime/src/bound_ui.rs:15`、`crates/axiom-runtime/src/bound_ui.rs:43`
- 問題: `prepare_assets` 直接使用內容提供的路徑，且檔案長度檢查與讀取分開進行。
- 證據: 對 `ui.images` 的每個 `path` 先呼叫 `std::fs::metadata(path)`，再呼叫 `std::fs::read(path)`。這條路徑由作者資料傳入，圖片解碼在讀取完成後才檢查尺寸。
- 影響: 載入來源不受信任的世界時，主機可能讀取並顯示其程序可讀的專案外 PNG。檔案若在檢查長度後增大，`read` 也可讀入超過 4 MiB 的資料。
- 建議修正: 用內容包的資產解析器取得路徑，檢查解析後的檔案位於允許的根目錄。開檔後最多讀取 `IMAGE_BYTES + 1`，超限時回傳帶圖片 ID 的錯誤。

### F11 [severity: medium] [angle: ai] [confidence: high] `narrative-check` 遇到合法的能力按鈕就中止分析

- 位置: `crates/axiom-runtime/src/narrative.rs:58`、`crates/axiom-runtime/src/narrative.rs:70`、`crates/axiom-runtime/src/gameplay.rs:308`
- 問題: 分析器將可見的能力按鈕交給只支援純玩法指令的執行器。
- 證據: 分析器收集所有條件成立且非 `Locale` 的 `BoundWidget::Button`，再以 `next.command(&command, tick)?` 探索。`Gameplay::apply` 對 `RuntimeCommand::Call` 一律回傳 `native capability calls must be dispatched by WorldRuntime`。
- 影響: ADV 世界只要有一顆可見的 `Call` 按鈕，即使它和結局無關，CLI 也可能拿不到其他分支已可證明的結局。
- 建議修正: 遇到需要原生系統的分支時保留已探索結果，回傳 `complete:false`，附上被略過的 widget ID 或能力名稱。加入合法能力按鈕與純敘事選項並存的測試。

### F12 [severity: medium] [angle: code] [confidence: high] Gameplay 在閒置固定步也複製可變狀態

- 位置: `crates/axiom-runtime/src/gameplay.rs:59`、`crates/axiom-runtime/src/gameplay.rs:401`、`crates/axiom-runtime/src/gameplay.rs:753`
- 問題: 無新輸入、無到期事件時，固定步仍進入複製及重建路徑。
- 證據: `step` 在無 fault 時執行 `let mut next = self.clone()`，複製含有變數、事件佇列與 trace 的狀態。它也複製 `compiled.inputs` 並重新收集 `held`。`BehaviorSystem::step` 每步再呼叫 `sync_scenes()`，後者建立成員遮罩。
- 影響: 已累積文字變數與 trace 的世界即使停在靜態對話，仍持續在固定步複製資料和配置記憶體。此次未量測每步耗時。
- 建議修正: 無輸入邊緣且無事件到期時走快速路徑，重用輸入儲存。只在場景啟用狀態變更時同步可見性，保留有操作時的失敗回復語意。

### F13 [severity: medium] [angle: ai] [confidence: high] 無變數滑桿的數值只由 GUI 保存

- 位置: `crates/axiom-runtime/src/bound_ui.rs:684`、`crates/axiom-runtime/src/bound_ui.rs:709`、`crates/axiom-runtime/src/gameplay.rs:330`、`crates/axiom-runtime/src/gameplay.rs:688`
- 問題: GUI 與 CLI 可以送出同一個 `Slide` 指令，但無變數滑桿沒有共用的已提交數值。
- 證據: GUI 在送出指令前更新 `state.slider_values`。`Gameplay::apply` 只在有 `s.variable` 時保存數值。`observation` 也只納入有變數的滑桿。
- 影響: CLI 成功改動滑桿所呼叫的能力後，GUI 讀值仍可能停在原位，`observe_delta` 也無法以滑桿 ID 驗證數值。GUI 指令若遭拒，介面仍可能顯示剛送出的值。
- 建議修正: 把無變數滑桿的已提交值放進 runtime，成功後才更新，並納入 `bindings` 觀察。GUI 只保存拖曳中的草稿。

### F14 [severity: medium] [angle: human] [confidence: high] FPS 相容刪除繞過 v2 的引用清理

- 位置: `crates/axiom-fps/src/editing.rs:53`、`crates/axiom-fps/src/editing.rs:175`、`crates/axiom-fps/src/content.rs:327`
- 問題: FPS 相容層自己刪除實體，並以不同方式判定 prefab 繼承的元件。
- 證據: `enemies.count` 從 resolved entities 找到 sentinel，再直接 `retain` 作者實體。`remove_obstacle` 只查作者實體本身的 `fps.cover`，同樣直接 `retain`。共用 v2 刪除路徑還會清理 scene membership 和 relations。
- 影響: 維護者把 sentinel 或 cover 加進場景後，相容刪除會因遺留引用而在批次驗證失敗。由 prefab 繼承 `fps.cover` 的障礙也會被相容操作回報為 `obstacle not found`。
- 建議修正: 先從 resolved components 找出穩定實體 ID，再交給共用 v2 刪除操作。用同一組 prefab 與場景 fixture 比對相容入口和編輯器刪除的結果。

### F15 [severity: low] [angle: ai] [confidence: high] Showcase 自動環繞在無 GUI 的情境中不會前進

- 位置: `crates/axiom-runtime/src/showcase.rs:270`、`crates/axiom-runtime/src/showcase.rs:323`、`crates/axiom-runtime/src/showcase.rs:603`
- 問題: `showcase.orbit` 可由 CLI 啟用，環繞位移卻只由 GUI 繪製產生。
- 證據: 能力指令只設定 `self.orbit`。固定步的 yaw 只讀取 `view.orbit` 輸入軸。`draw_ui` 才會依 `stable_dt` 算出增量並送出 `view` 指令。
- 影響: 無 GUI 的 scenario 執行 `showcase.orbit {enabled:true}` 後，即使前進多個 tick，相機也維持原位，metrics 仍顯示 `orbit:true`。
- 建議修正: 在固定步中依 `self.orbit` 和 `FIXED_DT` 推進 yaw，GUI 只送切換指令。加入無 GUI 的相機位姿測試。
