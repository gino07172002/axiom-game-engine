# R5 Physics, combat, navigation and generic gameplay systems — Codex review

## 摘要

程式正確性方面，共享戰鬥的事件突發可中止模擬，合法的物理操作可產生無法還原的 checkpoint，trigger 也有誤停與誤判離開的情況。  
AI 操作方面，多數系統提供具名查詢與執行期動作，但 `interact.use` 可能在事件失敗後仍回報成功，Tween 也可能漏掉已完成的播放事件。  
人類交接方面，FSM 的編輯器表單與公開 schema 各自維護動作清單，已出現可用欄位與公開說明不一致的情況。  
共同編輯方面，`expected_rev` 有修訂衝突檢查，但部分 FSM 錯誤要等到 runtime 啟用才會被發現，導航、路徑及相機的熱重載也可能改變正在執行的行為。  
效能方面，確認了導航工作量漏計及選取物件時同步搜尋的路徑。16 ms 預算未實測。

## Findings

### F1 [severity: high] [angle: code] [confidence: high] 共享戰鬥可在傷害已結算後塞滿事件佇列並凍結模擬
- 位置: `crates/axiom-runtime/src/combat.rs:58`、`crates/axiom-runtime/src/combat.rs:95`、`crates/axiom-combat/src/lib.rs:217`
- 問題: 戰鬥的受理上限高於跨套件事件匯流排的容量，且傷害會先於事件發布提交。
- 證據: `submit` 接受每步至多 4096 筆 hit。`Scene::resolve` 先以同一快照判定資格，再更新 HP。runtime 隨後逐筆發布 `combat.hit`，擊殺再發布 `combat.defeated`。跨套件事件佇列在第 129 筆設定 `fault`，後續固定步進在看到該故障時直接返回。
- 影響: 匯出 `combat.hit` 的世界若有 129 名有效射手同一步命中，傷害已經生效，部分事件未送出，接下來的模擬也停止。
- 建議修正: 提交 HP 前先計算並保留整批事件的容量。容量不足時讓有界 FIFO 分步交付，保留原始 tick 與順序。若待送容量也不足，在修改 HP 前拒絕整批並回報超出哪個上限。

### F2 [severity: high] [angle: collab] [confidence: high] FSM 的無效參照可通過 `preview` 並寫入修訂
- 位置: `crates/axiom-runtime/src/fsm.rs:454`、`crates/axiom-runtime/src/fsm.rs:471`、`crates/axiom-runtime/src/fsm.rs:514`、`crates/axiom-runtime/src/fsm.rs:953`
- 問題: FSM 把可在 authoring 階段判定的跨物件檢查留到 runtime 建構。
- 證據: `register` 只對 `fsm.machines` 呼叫 `Machines::validate`，對 `fsm.agent` 則只解析並檢查 `machine` 的 ID 格式。機器是否存在、代理是否有 `core.transform`、`emit` 是否有相容的事件宣告，都在 `FsmSystem::new` 才檢查。`preview` 與 `apply` 走 `World::compile`，不會建立該系統。
- 影響: AI 以正確的 `expected_rev` 把代理指向合法格式但不存在的機器。`preview` 通過，`apply` 寫入修訂，編輯器卻無法啟用該修訂。
- 建議修正: 把機器、必要元件和事件參照檢查提到共用的 registry world validator，回傳指向代理或狀態欄位的 `Diagnostic`。用同一筆 `machine` 編輯驗證 CLI 與編輯器都會在提交前拒絕。

### F3 [severity: high] [angle: code] [confidence: high] `once` trigger 把同一步的多名進入者誤算成多次事件
- 位置: `crates/axiom-runtime/src/trigger.rs:583`、`crates/axiom-runtime/src/trigger.rs:609`
- 問題: 預算預檢與實際發送對 `once` 使用不同的計數規則。
- 證據: 預檢逐筆讀取同一個尚未更新的 `z.enters` 或 `z.exits`，為所有符合的變動累加 `events`。實際發送則在第一筆之後增加計數，跳過同一方向的其餘變動。超過 64 筆時，預檢會設 `halted`，整步不發事件。
- 影響: 65 名符合篩選的實體同時進入一個 `once` 區域。原應只發出一次的進入事件完全沒送出，其他 trigger 也停止更新。
- 建議修正: 預檢為每個 zone 分別暫記當步是否已有 enter、exit 入列，與發送共用同一判斷。加入 65 名進入者只觸發一次的回歸測試。

### F4 [severity: high] [angle: code] [confidence: high] 合法物理衝量可產生存得出卻讀不回的 checkpoint
- 位置: `crates/axiom-runtime/src/physics.rs:370`、`crates/axiom-runtime/src/physics.rs:1140`、`crates/axiom-runtime/src/physics.rs:1258`、`crates/axiom-runtime/src/physics.rs:1299`、`crates/axiom-runtime/src/physics.rs:1321`、`crates/axiom-runtime/src/physics.rs:1392`
- 問題: 存檔容許的剛體速度範圍大於讀檔容許的範圍。
- 證據: `impulse` 檢查輸入向量後直接呼叫 `apply_impulse`，結果速度未受 `MAX_SPEED` 限制。存檔直接序列化 Rapier 的速度，驗證也只要求線速度有限。讀檔則要求線速度與角速度的每個分量都不超過 `MAX_SPEED`。
- 影響: 讓質量為 `0.001 kg` 的靜止動態剛體承受 `2 N·s` 的中心衝量，立即儲存可得到成功回覆，之後卻因速度高於 `1000 m/s` 而無法還原。
- 建議修正: 為 checkpoint 的存取共用一套速度驗證。若 `MAX_SPEED` 是作者輸入上限，替 checkpoint 定義涵蓋有效模擬狀態的範圍，並加入小質量剛體的存讀往返測試。

### F5 [severity: medium] [angle: ai] [confidence: high] `interact.use` 在事件失敗後仍消耗次數並回報成功
- 位置: `crates/axiom-runtime/src/interact.rs:506`、`crates/axiom-runtime/src/interact.rs:536`、`crates/axiom-runtime/src/interact.rs:633`
- 問題: 一次性與冷卻狀態先行提交，事件失敗只留下觀察用的 `fault`。
- 證據: `apply` 先增加 `uses`、更新 `ready_at` 並寫入 `recent`，才執行 `RuntimeCommand::Emit`。錯誤分支只記錄文字，`use_command` 仍回傳 `Ok`，並在結果列出事件名稱。
- 影響: 一次性門鎖的事件規則超出執行預算時，開門效果未提交。CLI 卻收到使用成功，重試也會因目標已用過而被拒絕。
- 建議修正: 讓 `apply` 回傳 `Result`，事件成功後才提交次數、冷卻與成功紀錄。CLI 傳回帶目標及事件名稱的錯誤，按鍵路徑將同一錯誤送到可觀察的 `fault`。

### F6 [severity: medium] [angle: code] [confidence: high] HP 歸零的 FSM 代理仍能攻擊
- 位置: `crates/axiom-runtime/src/fsm.rs:426`、`crates/axiom-runtime/src/fsm.rs:700`、`crates/axiom-runtime/src/fsm.rs:735`
- 問題: FSM 對目標使用存活條件，對發動攻擊的代理只檢查場景是否啟用。
- 證據: `nearest_slot` 過濾 HP 已歸零的目標。`step` 只在 `compiled.enabled[slot]` 為假時略過代理，`ActionDef::Attack` 分支隨後直接扣目標生命值。
- 影響: 只有 `attack` 狀態的代理被打倒後，只要實體仍在啟用場景，就可以繼續按原冷卻週期扣除玩家 HP。
- 建議修正: 保留死亡時的狀態轉移、事件與動畫，並在執行 `Attack` 前檢查施術者的 HP。加入零血攻擊者仍能走死亡轉移、但無法造成傷害的測試。

### F7 [severity: medium] [angle: code] [confidence: high] 導航失敗路徑的直線化工作未計入每步預算
- 位置: `crates/axiom-runtime/src/nav_agent.rs:667`、`crates/axiom-runtime/src/nav_agent.rs:689`、`crates/axiom-runtime/src/nav_agent.rs:1085`
- 問題: 一項路徑工作可以耗用直線化預算後失敗，外層迴圈卻仍以先前的用量繼續服務請求。
- 證據: 每次找到路徑會執行 `search.path`，並給 `straighten` 至少 `MIN_STRAIGHTEN_WORK`。只有 `Some(spent) if room` 分支增加 `self.used`。回傳 `None` 或插入起點會超過 waypoint 上限時，直接以 `path_too_long` 失敗。
- 影響: 多名代理同一步找到過多轉角的路徑時，可反覆耗用未計帳的工作。`observe` 的 `budget.last` 與 `max` 也會低報。
- 建議修正: 讓 `straighten` 在成功及失敗時都傳回已用工作量，先計帳再處理結果。剩餘額度不足時把直線化留到下一步，並對回溯及轉角掃描設定共用上限。

### F8 [severity: medium] [angle: code] [confidence: high] `nav.stop` 留下待處理項，重送 `nav.go` 可累積重複項
- 位置: `crates/axiom-runtime/src/nav_agent.rs:542`、`crates/axiom-runtime/src/nav_agent.rs:553`、`crates/axiom-runtime/src/nav_agent.rs:596`
- 問題: `queued` 只是一個代理旗標，無法區分舊請求與同一代理的新請求。
- 證據: `cancel` 清除 `queued`，卻不從 `VecDeque` 移除代理索引。下一次 `enqueue` 會追加相同索引。`begin_next` 看到舊索引時只讀當前 `queued`，略過取消項時也不增加 `used`。
- 影響: 暫停期間反覆交替下達 `nav.go` 和 `nav.stop`，同一個代理可累積多個項目。恢復後，最新請求可能借用舊位置插隊，大量取消項也可在一步內被掃完。
- 建議修正: `cancel` 同時移除該代理的待處理項，維持每個代理最多一個 FIFO 項目。測試停止、重送和兩個代理交錯排隊的順序。

### F9 [severity: medium] [angle: code] [confidence: high] 選取導航代理會在編輯器畫面更新時同步執行路徑搜尋
- 位置: `crates/axiom-runtime/src/nav_agent.rs:43`、`crates/axiom-runtime/src/nav_agent.rs:1114`
- 問題: 選取物件即可觸發有界但同步的 A* 與路徑直線化。
- 證據: viewport 的選取物件繪製路徑直接呼叫 `preview_path`。快取未命中時，該函式在同一呼叫中建立 `GridSearch`、執行最多 65,536 次展開，再做直線化。快取命中也會複製 waypoint `Vec`。
- 影響: 在大格網首次選取代理，或起點跨格使快取失效時，繪製會等搜尋返回才繼續。程式碼沒有設定 16 ms 截止時間。
- 建議修正: 把搜尋改為顯式、可取消且有 watchdog 的預覽工作，以輸入鍵回收結果。繪製期間讀取已完成的共用 waypoint slice，並顯示工作狀態。

### F10 [severity: medium] [angle: collab] [confidence: high] `path.set_speed` 會蓋過後續修訂的作者速度
- 位置: `crates/axiom-runtime/src/path_follow.rs:346`、`crates/axiom-runtime/src/path_follow.rs:637`、`crates/axiom-runtime/src/path_follow.rs:733`
- 問題: 熱重載有意保留播放進度，但也無條件保留同一跟隨者的速度覆寫，即使作者已修改速度。
- 證據: 建構時用 `def.speed` 初始化速度。`authored` 比對元組只含 `start`、`start_fraction`、`end`、`paused`。只要進度符合保留條件且 `of.speed_set` 為真，`transfer` 就把舊的 runtime 速度寫回。
- 影響: AI 在執行期將速度設為 `8 m/s`，人類在編輯器將作者速度改為 `2 m/s`。新修訂已啟用，但跟隨者仍以 `8 m/s` 移動。
- 建議修正: 另外保存作者速度，僅在新舊作者速度相同時延續 runtime 覆寫。速度修改時保留位置、進度和暫停狀態。

### F11 [severity: medium] [angle: collab] [confidence: high] 相機熱重載只驗證執行期目標 ID 是否仍存在
- 位置: `crates/axiom-runtime/src/camera_rig.rs:377`、`crates/axiom-runtime/src/camera_rig.rs:711`
- 問題: 執行期重新指定跟隨目標時有幾何和元件限制，熱重載沿用該目標時沒有套用同一組限制。
- 證據: `plan_set` 拒絕相機自身、相機後代、無 `core.transform` 的實體及另一台 follow camera。`transfer` 在相機元件未改且 `target_set` 時，只憑新世界的 `indices.get(id)` 就恢復目標。
- 影響: AI 在執行期把相機的目標從 A 改為 B，接著人類把 B 移到相機下面。作者目標仍為 A，修訂可以啟用，但相機會開始追逐隨自身移動的子實體。
- 建議修正: 共用目標合格性檢查。舊的 runtime 目標在新修訂已不合格時回到作者目標，並在 `camera.inspect` 提供一則簡短的失效原因。

### F12 [severity: medium] [angle: collab] [confidence: high] 無關修訂會讓導航代理忘記終點曾被吸附
- 位置: `crates/axiom-runtime/src/nav_agent.rs:428`、`crates/axiom-runtime/src/nav_agent.rs:636`、`crates/axiom-runtime/src/nav_agent.rs:799`、`crates/axiom-runtime/src/nav_agent.rs:1271`
- 問題: 同格網熱重載時，保留的 waypoint 缺少控制最後一段行為的 `goal_snapped`。
- 證據: 新代理的 `goal_snapped` 初值為 `false`。`transfer` 保留 `waypoints`、`next` 和 `planned_for`，沒有複製該旗標。`steer` 在最後一段且旗標為 `false` 時，會使用目標實體目前的位置。
- 影響: 代理正走向牆邊已吸附的可走終點時，人類提交一筆與導航無關的修訂。代理接著會轉向牆內原目標，可能在牆邊卡住。
- 建議修正: 保留路徑時一併保留 `goal_snapped`，並加入同一格網、被障礙阻擋的實體目標及無關熱重載的測試。

### F13 [severity: medium] [angle: code] [confidence: high] 旋轉 box trigger 的格網候選範圍小於離開容差所需範圍
- 位置: `crates/axiom-runtime/src/trigger.rs:46`、`crates/axiom-runtime/src/trigger.rs:60`、`crates/axiom-runtime/src/trigger.rs:522`
- 問題: 精確檢查對 box 的三個半軸各增加 `exit_margin`，格網粗篩卻只在原包圍球半徑上加一次。
- 證據: `contains` 比較 `(inverse * d).abs()` 與 `half + grow`。粗篩的 `reach` 則是 `zone.shape.reach() + zone.margin`，而 box 的 `reach()` 回傳 `half.length()`。
- 影響: 已在區內的角色走到旋轉 box 擴張後的角落時，可能進入粗篩完全沒查到的格子，尚在設定的容差範圍內就觸發 `on_exit`。
- 建議修正: box 使用 `(half + Vec3::splat(margin)).length()` 作為保守半徑。加入旋轉 45 度且擴張角落跨格的回歸測試。

### F14 [severity: medium] [angle: code] [confidence: high] Tween 的新一輪播放可在上一輪事件排隊時漏送 `on_finish`
- 位置: `crates/axiom-runtime/src/tween.rs:630`、`crates/axiom-runtime/src/tween.rs:642`、`crates/axiom-runtime/src/tween.rs:735`
- 問題: 完成事件以播放器的單一旗標去重，導致同一播放器的兩次完成被當成同一件事。
- 證據: `step` 只有在 `!player.queued` 時才新增完成事件，每步最多取出 64 筆。`play` 允許在舊事件仍排隊時重新開始，下一步也會先推進播放，再處理佇列。
- 影響: 大量 clip 同步完成後，排在第 65 筆以後的短 clip 若在下一步前被重新播放，且下一步又播放完畢，就只會送出第一次的完成事件。
- 建議修正: 在舊事件送出前，對會開始新一輪的 `tween.play` 回傳可重試的錯誤。加入超過發送上限、積壓期間重播的測試。

### F15 [severity: low] [angle: human] [confidence: high] FSM 編輯器表單與公開 schema 已列出不同的動作和條件
- 位置: `crates/axiom-runtime/src/fsm.rs:251`、`crates/axiom-runtime/src/fsm.rs:953`
- 問題: 同檔維護兩份功能清單，新增行為時容易只更新其中一份。
- 證據: `editor_kinds` 提供 `wander`、`face` 和 `clip_finished`。`register` 公開的 `fsm.machines` 說明省略這三項與狀態的 `clip`、`clip_loop`，`fsm.agent` 說明也只列出 `machine`。
- 影響: 開發者可在 Graphs 建出等待動畫播完的轉移，交接給只查 `schema fsm.machines` 的代理時，該代理無法從公開介面取得對應的條件和片段欄位。
- 建議修正: 由同一組動作與條件描述產出公開 schema 及表單選項，補齊狀態與代理欄位。測試兩個介面公開的種類一致。
