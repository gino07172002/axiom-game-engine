# R10 Docs, scripts and onboarding entry points — Codex review

## 摘要

- 程式正確性：內容重建腳本可能刪除既有資料庫與備份，ADV smoke 也會寫入一般遊玩使用的存檔目錄。
- AI 可用性：CLI 已提供探索、預覽、重試與觀察所需的操作，但入門範例用錯資料庫，部分協定說明也會讓 agent 送出無效請求或漏掉啟用診斷。
- 人類交接：架構邊界已有說明。安裝檔驗證、PowerShell 版本需求與效能報告的解讀仍有缺口。
- AI–人類共編：底層提供 CAS、修訂歷史與逐欄合併，但快速流程沒有把預覽結果綁定到提交，部分 parity 腳本也沒有驗證 bridge 屬於本次啟動的編輯器。

## Findings

### F1 [severity: high] [angle: code] [confidence: high] 內容重建會刪除指定資料庫及同前綴的備份

- 位置: `scripts/build-street.ps1:7`、`scripts/build-street.ps1:15`、`scripts/build-plaza.ps1:8`、`scripts/build-plaza.ps1:16`
- 問題: `-Db` 接受任意路徑，重建前會以萬用字元刪除檔案。
- 證據: 兩支腳本都先依 `$Db` 建立父目錄，再執行 `Remove-Item "$Db*" -ErrorAction SilentlyContinue`。刪除範圍未限制在測試目錄，且早於種子匯入及驗證。
- 影響: 傳入 `-Db data\world.sqlite` 會刪除玩家的資料庫及同前綴的 `world.sqlite.bak`。後續建置失敗時，原資料已被刪除。
- 建議修正: 預設建立每次執行專用的新目錄。保留 `-Db` 時，若指定路徑已有資料庫或 SQLite sidecar，直接拒絕並要求改用新路徑。

### F2 [severity: high] [angle: code] [confidence: high] ADV smoke 的測試存檔會覆寫玩家存檔

- 位置: `scripts/m1-smoke-test.ps1:9`、`scripts/m1-smoke-test.ps1:39`、`scripts/m1-smoke-test.ps1:73`
- 問題: 時間戳只隔離 SQLite 檔名，測試仍共用 `data/saves`。
- 證據: 腳本把 DB 放在 `data/`，重播含 `save` 操作的 ADV scenarios，並即時儲存固定 slot `live`。CLI scenario 與一般 Play 都從 DB 的父目錄取 `saves`，路徑接著依世界 ID 和 slot 決定，見 `crates/axiom-cli/src/lib.rs:860`、`crates/axiom-runtime/src/app.rs:1819`、`crates/axiom-runtime/src/checkpoint.rs:228`。`examples/adv-rescue.scenario.json:9` 也寫入固定 slot `key`。
- 影響: 同在 `data/` 的 ADV 遊玩 DB 若已有 `key` 或 `live`，smoke 會覆寫該 slot。再跑一輪時，原玩家存檔也會從 `.bak` 被替換。
- 建議修正: 把 `$m1Db` 放進每次建立的 `$m1Dir`，讓 headless scenario 與即時 Play 共用該次測試專用的 `saves/`。

### F3 [severity: high] [angle: ai] [confidence: high] README 導覽的寫入與還原落到預設世界

- 位置: `README.md:33`、`README.md:42`、`README.md:54`、`README.zh-TW.md:33`、`README.zh-TW.md:42`、`README.zh-TW.md:54`
- 問題: 導覽說每條指令都使用 `lab.sqlite`，實際只有第一條指定 `--db lab.sqlite`。
- 證據: `set`、`call`、`scenario` 與 `undo` 都省略 `--db`。每次 CLI 呼叫各自解析目標，未指定時開啟 `data/world.sqlite`，見 `crates/axiom-cli/src/lib.rs:565`。
- 影響: 逐行照跑時，診斷與 scenario 會檢查錯誤的世界。`undo 1` 會嘗試以預設世界的 revision 1 建立一個新的還原 revision，覆蓋目前生效的世界定義。
- 建議修正: 在兩版 README 的每條導覽指令都明寫 `--db lab.sqlite`，並使用同一份範例來源生成或核對兩版指令。

### F4 [severity: medium] [angle: collab] [confidence: high] Parity 腳本可能修改已開啟的人類編輯器

- 位置: `scripts/editor-world-parity.ps1:32`、`scripts/editor-world-parity.ps1:67`、`scripts/editor-world-parity.ps1:78`、`scripts/street-editor-parity.ps1:32`、`scripts/street-editor-parity.ps1:60`
- 問題: 就緒判定把指定埠上回應的任何 GPU 編輯器視為本次測試程序。
- 證據: `Wait-Editor` 以 `observe` 回覆的 `gpu` 與 `editor.mode` 放行，未核對 DB 或程序身分。接著直接送出 `editor_view` 寫入指令。新程序在初始化時才綁定埠，見 `crates/axiom-runtime/src/app.rs:732`、`crates/axiom-runtime/src/bridge.rs:55`。
- 影響: 若傳入的 `-Port` 已被另一個處於 Edit mode 的編輯器使用，且測試子程序仍在啟動，第一筆 `world.set_id corner` 或 `object.cube` 可以先寫到既有編輯器。後續即使測試因綁定失敗而中止，該筆修訂已提交。
- 建議修正: 啟動前拒絕已被占用的埠，並在首筆寫入前透過同一 bridge 的 `query` 驗證本次測試 DB 的唯一標記。

### F5 [severity: medium] [angle: collab] [confidence: high] 入門流程讓預覽與提交各自使用當時的最新修訂

- 位置: `README.md:116`、`README.md:119`、`README.zh-TW.md:111`、`README.zh-TW.md:114`、`AGENTS.md:15`
- 問題: 預覽後的 ACL 提交與還原範例都省略 `--expected-rev`。ACL 速查表還把 `undo REV` 列為讀取操作。
- 證據: ACL 只有在提供 `expected_rev` 時才核對先前讀取的修訂，見 `crates/axiom-core/src/acl.rs:2347`。`undo_in` 同樣只在有傳值時檢查 CAS，之後把目標修訂的整份世界插入為最新修訂，見 `crates/axiom-core/src/store.rs:644`、`crates/axiom-core/src/store.rs:654`。
- 影響: 人類在預覽和提交之間新增符合 selector 的物件，ACL 可能修改預覽中未出現的物件。無保護的還原也可能把預覽後的人類修改一起還原。
- 建議修正: 示範讀取修訂 `R`，預覽與提交皆帶 `--expected-rev R`。遇到 `revision_conflict` 時重查並重新預覽。將 `undo` 移至寫入區，示範以目前確認過的修訂保護還原。

### F6 [severity: medium] [angle: code] [confidence: high] Parity 比對可使用上次匯出的世界，並忽略大小寫差異

- 位置: `scripts/editor-world-parity.ps1:109`、`scripts/editor-world-parity.ps1:115`、`scripts/street-editor-parity.ps1:92`、`scripts/street-editor-parity.ps1:98`
- 問題: 腳本重用固定匯出路徑，未檢查兩次 `export` 的結束碼，且以 PowerShell 預設忽略大小寫的 `-eq` 比對文字。
- 證據: 兩支腳本都把 `export` 的輸出送至 `Out-Null`，隨即讀取 `via-editor.json` 與 `via-acl.json`。檔案名固定，而註解承諾逐位元一致。
- 影響: 匯出在寫檔前失敗時，舊檔仍可通過比對。即使兩個檔案均為本次輸出，`Door` 與 `door` 這類差異也會被放過。
- 建議修正: 使用本次執行專用的匯出路徑，逐一檢查結束碼，再比對兩個檔案的 SHA-256。

### F7 [severity: medium] [angle: code] [confidence: high] Bootstrap 直接解包與執行未驗證的工具鏈下載

- 位置: `scripts/setup.ps1:11`、`scripts/setup.ps1:14`、`scripts/setup.ps1:18`、`scripts/setup.ps1:20`
- 問題: 安裝只檢查下載程式的結束碼，缺少檔案完整性驗證。
- 證據: 腳本下載 MinGW 封存後直接呼叫 `tar.exe`，下載 `rustup-init.exe` 後立即執行。兩條路徑都沒有雜湊或簽章比對。
- 影響: 若來源回傳被替換的檔案，只要 HTTP 下載成功，bootstrap 就會以開發者身分使用該工具鏈或執行該安裝檔。
- 建議修正: 固定下載版本與受信任的 SHA-256，在解包或執行前比對。失敗時回報檔名與預期雜湊，並停止安裝。

### F8 [severity: medium] [angle: code] [confidence: high] 打包 smoke 可能無限等待玩家程序

- 位置: `scripts/package-smoke-test.ps1:53`、`scripts/package-smoke-test.ps1:59`
- 問題: 玩家程序的等待沒有期限，腳本也沒有終止逾時程序的路徑。
- 證據: `Start-Process -Wait -PassThru` 同步等待程序結束。`finally` 只處理環境變數。`--smoke-frames` 限制畫幀數，無法限制卡在產生畫幀前的等待。
- 影響: 若玩家在 GPU 初始化時停住，整個驗收會卡在第一個出問題的內容包，無法產出該包的逾時診斷。
- 建議修正: 改用 `-PassThru` 和有期限的 `WaitForExit`。逾時時終止本次子程序，並在錯誤中列出內容包與 stderr 路徑。

### F9 [severity: medium] [angle: code] [confidence: high] 效能摘要會混合 debug 與 release 樣本

- 位置: `scripts/perf-summary.ps1:48`、`scripts/perf-summary.ps1:51`、`docs/perf-baseline.zh-TW.md:16`
- 問題: 文件推薦的 `bench-*.jsonl` 涵蓋多種 profile，但摘要只按 pack 分組。
- 證據: `$set` 依 `pack` 篩選全部輸入列，標題卻使用 `$set[0].build_profile`，接著用整組資料計算中位數與範圍。
- 影響: 同時傳入某個 pack 的 debug 與 release 報告，會得到標為單一 profile 的混合數值，足以讓後續 A/B 比較判錯。
- 建議修正: 以 `(pack, build_profile)` 分組並各自輸出樣本數。標題採用分組鍵。

### F10 [severity: medium] [angle: ai] [confidence: high] 協定入門把 request ID 說成適用於所有請求

- 位置: `README.md:64`、`README.zh-TW.md:64`、`docs/user-guide.zh-TW.md:115`
- 問題: README 宣稱所有請求都使用 CAS 和 request-ID 重試，使用指南也將冪等重試概括套用到 ACL。
- 證據: CLI 的 `--request-id` 將當前請求包成 `Execute`，`acl` 則產生 `Request::Acl`，見 `crates/axiom-cli/src/lib.rs:578`、`crates/axiom-cli/src/lib.rs:727`。持久化 `execute_once` 只接受 `Apply` 和 `Undo`，見 `crates/axiom-core/src/store.rs:679`。
- 影響: Agent 對 `acl` 或 `select` 加上 `--request-id` 會收到拒絕。從 ACL 提交逾時恢復時，也缺乏判斷前一次寫入是否成功的操作說明。
- 建議修正: 明列可使用持久化 receipt 的操作，並給一條可執行的 `apply --request-id` 範例。補充 ACL 回覆遺失時可先查修訂歷史與差異，再決定是否重送。

### F11 [severity: medium] [angle: code] [confidence: high] Parity 截圖走同步 GPU 讀回且未驗證寫檔完成

- 位置: `scripts/editor-world-parity.ps1:95`、`scripts/editor-world-parity.ps1:102`、`scripts/street-editor-parity.ps1:81`、`scripts/street-editor-parity.ps1:86`
- 問題: 腳本採用舊的 `editor_view {capture}`，收到路徑後用固定延遲等待，沒有驗證 PNG。
- 證據: 舊操作回覆 `capture_ready: "written on the next rendered frame"`，見 `crates/axiom-runtime/src/app.rs:1778`。渲染路徑同步呼叫 `device.poll(wgpu::Maintain::Wait)`、`rx.recv()`，見 `crates/axiom-runtime/src/render.rs:1201`。`docs/scene-editor.zh-TW.md:112` 已記錄該路徑在 debug 會讓一幀多停數百毫秒。

- 建議修正: 改送完成寫檔才回覆的 `screenshot` 請求，使用本次執行專用路徑，並檢查 `ok` 與檔案存在後再記入報告。

### F12 [severity: low] [angle: human] [confidence: high] PowerShell 版本需求會到腳本執行中途才暴露

- 位置: `scripts/m3-smoke-test.ps1:45`、`scripts/m3-smoke-test.ps1:55`、`scripts/build-m4-content.ps1:21`、`scripts/shader-smoke-test.ps1:70`
- 問題: 這些腳本使用 Windows PowerShell 5.1 不支援的 `ConvertFrom-Json -AsHashtable`，但沒有在入口檢查版本。
- 證據: M3 smoke 先執行 scenario 與 GPU 基準截圖，之後才呼叫 `-AsHashtable`。Shader 指南有註明 PowerShell 7，對應腳本本身沒有版本檢查。M4 指南只提供重建腳本名稱，見 `docs/m4-composition.zh-TW.md:71`。
- 影響: 依 Windows onboarding 使用 5.1 的開發者會先花時間建資料庫及產出截圖，再遇到參數錯誤。
- 建議修正: 在需要該參數的腳本加 `#Requires -Version 7.0`，並在相應文件給出 `pwsh -File` 的執行方式。

### F13 [severity: low] [angle: ai] [confidence: high] 即時觀察範例看不到啟用失敗的原因

- 位置: `README.md:118`、`README.zh-TW.md:113`
- 問題: 範例只投影 `/rev`，也沒示範用游標接續輪詢。
- 證據: `observe_delta` 使用明寫的 `fields` 決定投影。未帶 `cursor` 時回傳 `reason: "initial"` 的快照，見 `crates/axiom-core/src/observe.rs:75`、`crates/axiom-core/src/observe.rs:102`、`crates/axiom-core/src/observe.rs:143`。

### F14 [severity: low] [angle: human] [confidence: high] 效能摘要把兩個 p95 的和當成總耗時 p95 的上界

- 位置: `scripts/perf-summary.ps1:25`、`scripts/perf-summary.ps1:29`、`docs/perf-baseline.zh-TW.md:133`
- 問題: 在舊報告缺少 `editor_main_ms` 時，腳本將 `commit_ms.p95 + request_ms.p95` 標為總耗時的 p95，註解與文件稱它為上界。
- 證據: 腳本直接相加兩個階段各自彙總的分位數。若兩個階段各有 4% 的慢樣本，且出現在不同編輯上，兩個階段各自的 p95 可以很低，但總耗時有 8% 的慢樣本。
- 影響: 舊版基準的尾端延遲可能被低估，和直接測得的新版 `editor_main_ms.p95` 比較時會混淆指標。
- 建議修正: 有逐筆資料時先加總每筆的兩個階段，再計算 p95。只有彙總值時將總耗時 p95 標為缺值，並移除上界描述。

### F15 [severity: low] [angle: human] [confidence: high] 貢獻者入口未列出內容編輯的 parity 驗收條件

- 影響: 只依貢獻者入口工作的開發者或 agent，可能為新功能補齊 GUI 和一般測試，卻遺漏可供無頭 agent 使用的 ACL 動詞與 parity test。
