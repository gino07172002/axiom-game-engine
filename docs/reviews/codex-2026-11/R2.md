# R2 Runtime host and lifecycle — Codex review

## 摘要

一般正確性：版本啟用有保留上一個可執行版本的機制，但即時 RPC 可阻塞視窗主執行緒，切換世界也可能沿用上一個世界的模擬狀態。  
AI 可用性：`observe` 能比對已提交與已生效的版本，但部分失敗、取消及重試路徑的回覆無法可靠反映操作結果。  
人工交接：跨套件事件有回歸測試，原生外掛介面仍允許修改超出交易回滾範圍的私有狀態。  
AI–人協作：一般編輯已有 CAS 衝突測試，但提案核准後的 Undo 可撤回其他作者的版本，`editor_view` 也可能在提交已排入後回報失敗。

## Findings

### F1 [severity: high] [angle: collab] [confidence: high] 核准重套提案後，Undo 可能一起撤回 AI 的變更
- 位置: `crates/axiom-runtime/src/app.rs:972`、`crates/axiom-runtime/src/app.rs:976`、`crates/axiom-runtime/src/app.rs:994`、`crates/axiom-runtime/src/app.rs:1130`
- 問題: Undo stack 記錄的版本可能早於核准交易真正套用的版本。
- 證據: `dispatch_write` 原樣轉交 `ResolveProposal.expected_rev`，但 `item.sent` 的版本一律取自 `chain_rev`。核准完成後，`finish_write` 以該值呼叫 `editor.record_apply(expected)`。GUI 的重套核准可傳入 `expected_rev: None`，這時交易會使用執行當下的最新版本。
- 影響: 編輯器在 rev 10 排入重套核准，AI 先提交 rev 11，提案再產生 rev 12。此時 GUI 的 Undo 可在 CAS 驗證 rev 12 成功後恢復 rev 10，同時撤掉 rev 11 的 AI 編輯。
- 建議修正: GUI 對未帶 `expected_rev` 的核准請求，送出時補上 `Some(chain_rev)`，保留已明確指定的版本。用現有 writer 測試的 gate 插入 AI 提交，驗證核准回報版本衝突。

### F2 [severity: high] [angle: code] [confidence: high] 即時 RPC 在主執行緒等待版本建置，逾時後仍可執行
- 位置: `crates/axiom-runtime/src/app.rs:2207`、`crates/axiom-runtime/src/app.rs:2576`、`crates/axiom-runtime/src/app.rs:2617`、`crates/axiom-runtime/src/app.rs:2655`、`crates/axiom-runtime/src/bridge.rs:92`
- 問題: 版本啟用原本在背景建置，但普通即時請求會把等待搬回視窗迴圈。
- 證據: `frame` 呼叫 `handle_command`，後者只在入口檢查 `deadline`，接著對一般即時請求呼叫 `finish_activation()`。該函式持續輪詢並睡眠，直到 `activation` 清空，之後直接執行請求。Bridge 對一般即時請求只等三秒。
- 影響: 建置期間送出 `Command` 會暫停畫面、輸入與模擬。若建置在呼叫端逾時後才完成，未帶版本條件的命令仍會改動狀態。
- 建議修正: 重用現有 deferred request 機制，每幀輪詢一次，執行前再檢查截止時間。逾時或啟用失敗時回傳結構化診斷，附上目標與目前生效的版本。

### F3 [severity: high] [angle: code] [confidence: high] 一條未完成的 loopback 連線可卡住所有請求與關閉
- 位置: `crates/axiom-runtime/src/bridge.rs:72`、`crates/axiom-runtime/src/bridge.rs:83`、`crates/axiom-runtime/src/bridge.rs:178`
- 問題: Bridge 逐條處理連線，沒有整筆請求的絕對截止時間，關閉也沒有 join 上限。
- 證據: 唯一的 listener worker 將 socket 設為 blocking，以 `take(1_048_577).read_line(...)` 讀取資料。`take` 限制位元組數，兩秒 socket timeout 限制個別讀取等待。`Drop` 設定旗標後直接 `join()`，而讀取中的連線不檢查旗標。
- 影響: 本機連線若持續零星送入未結束的一行，後來的 `observe`、查詢與編輯都會排在後方。關閉視窗時也要等同一個 worker 返回。
- 建議修正: 為每條連線設定絕對讀取期限，讀取迴圈定期檢查停止旗標，並對關閉採用限時 join。保留既有分段讀取測試，再加入慢速未終止請求的測試。

### F4 [severity: high] [angle: collab] [confidence: high] `editor_view` 可在寫入已排定後回報請求失敗
- 位置: `crates/axiom-runtime/src/app.rs:1751`、`crates/axiom-runtime/src/app.rs:1758`、`crates/axiom-runtime/src/app.rs:2629`
- 問題: 同一請求的 `capture` 驗證排在編輯命令之後，錯誤回覆與提交結果可以分離。
- 證據: `runtime_request` 先呼叫 `editor_action`，之後才驗證 `capture` 名稱及建立目錄。`handle_command` 只在 `Ok` 分支把回覆掛到待提交的寫入。`Err` 分支立即回錯，先前排入的寫入仍留在佇列。
- 影響: AI 以 `object.cube` 搭配非法截圖名稱時會收到錯誤，但立方體仍可提交。修正名稱後重送整筆請求，可再建立一個立方體。
- 建議修正: 先完成 `capture` 名稱驗證及目錄準備，再執行編輯命令。加入非法名稱時 revision 與物件數都不變的回歸測試。

### F5 [severity: medium] [angle: code] [confidence: high] 以不同 `world.id` 取代世界時，仍會移轉舊世界的實體狀態
- 位置: `crates/axiom-runtime/src/world.rs:1222`、`crates/axiom-runtime/src/world.rs:1243`、`crates/axiom-runtime/src/world.rs:1313`
- 問題: `adopt` 只用世界 ID 限制部分狀態移轉，實體和一般原生系統仍依各自的 ID 配對。
- 證據: 即使 `world.id` 改變，程式仍複製 tick，依實體 ID 沿用 handle，對相同 authored transform 沿用即時 transform，並計入舊世界的生命值差額。原生 `system.transfer` 也在世界 ID 檢查之前執行。
- 影響: 兩個世界若都有相同初始位置的 `hero`，切換後的新世界可從前一個 `hero` 移動後的位置與受傷後的生命值開始。
- 建議修正: 用一次世界 ID 比對決定是否允許模擬狀態移轉。不同世界使用新建狀態，並測試兩個世界具有重複實體 ID 的情況。

### F6 [severity: medium] [angle: ai] [confidence: high] 批次預檢漏查 context，`execute` 重送可重做已成功的前綴
- 位置: `crates/axiom-runtime/src/world.rs:743`、`crates/axiom-runtime/src/world.rs:796`、`crates/axiom-runtime/src/world.rs:917`、`crates/axiom-runtime/src/app.rs:1812`
- 問題: `input.activate` 的預檢與正式執行驗證不同，部分執行的結果也沒有重試 receipt。
- 證據: `check_call` 對 `input.activate` 只檢查 context 資源是否存在。正式執行透過 `activate(args)` 檢查指定的 context ID。`batch` 的執行迴圈明確保留已套用的前綴，而 `execute` 在內層回傳 `Err` 時會於寫入 receipt 前返回。
- 影響: 批次先用事件累加變數，後面切換到格式合法但不存在的 context。第一次呼叫已累加一次，AI 用相同 `request_id` 重送後可再累加一次。
- 建議修正: 讓預檢與正式執行共用 context ID 驗證。對仍可能部分套用的批次，回傳 `applied_count` 和失敗索引，並儲存該結果供相同 `request_id` 重試。

### F7 [severity: medium] [angle: code] [confidence: high] 即時 checkpoint 存讀在視窗執行緒同步完成
- 位置: `crates/axiom-runtime/src/app.rs:1843`、`crates/axiom-runtime/src/app.rs:2972`、`crates/axiom-runtime/src/checkpoint.rs:141`、`crates/axiom-runtime/src/checkpoint.rs:171`、`crates/axiom-runtime/src/checkpoint.rs:209`
- 問題: RPC 存讀與遊戲內快速存讀會在同一幀等候檔案 I/O 與 checkpoint 處理。
- 證據: GUI 和 RPC 都直接呼叫 `save_slot` 或 `load_slot`。存檔擷取整個 checkpoint、序列化並執行 `sync_all()`。讀檔同步讀取及解析 JSON，然後編譯 snapshot 並呼叫 `WorldRuntime::new`。
- 影響: 較大的存檔或儲存裝置延遲會讓視窗與模擬等待整筆操作完成。程式沒有為這條路徑限制主執行緒等待時間。
- 建議修正: 將編碼、檔案 I/O 和替代 runtime 建置移入有界工作。主執行緒擷取一致的存檔狀態，並在確認讀檔仍屬於目前 session 與版本後接手結果。

### F8 [severity: medium] [angle: code] [confidence: high] 模型監看在畫幀時同步遞迴掃描目錄
- 位置: `crates/axiom-runtime/src/app.rs:2128`、`crates/axiom-runtime/src/asset_reload.rs:96`、`crates/axiom-runtime/src/asset_reload.rs:157`、`crates/axiom-runtime/src/asset_reload.rs:294`
- 問題: 模型重建雖在背景執行，偵測模型變更的檔案系統掃描仍在主執行緒。
- 證據: `watch_due` 每秒為各來源呼叫 `stamp`。`stamp` 呼叫 `companions`，後者同步遞迴執行 `read_dir` 和 `metadata`，並排序收集的檔案。掃描以來源為單位，同資料夾可重複走訪。
- 影響: 監看開啟後，多個模型共用大型資料夾時，同一幀要依序等候重複掃描，即使所有檔案都沒有變更。
- 建議修正: 每次只排入一個可取消的監看掃描工作，依資料夾去重。主執行緒只輪詢結果，再沿用現有的重載工作。

### F9 [severity: medium] [angle: code] [confidence: high] Writer watchdog 觸發後，編輯改由主執行緒同步提交
- 位置: `crates/axiom-runtime/src/app.rs:1259`、`crates/axiom-runtime/src/app.rs:2250`、`crates/axiom-runtime/src/app.rs:2345`、`crates/axiom-runtime/src/app.rs:4531`
- 問題: 背景 writer 發生停滯後，後續寫入失去背景執行與 watchdog 保護。
- 證據: watchdog 以 `self.writes.take()` 移除 writer。後續 `editor_action` 走入 `editor_action_now`，直接呼叫 `self.store.execute`。既有測試明確驗證停滯後下一筆編輯在主執行緒提交。
- 影響: 舊 writer 仍可能完成提交時，下一筆 GUI 編輯會同步等待 SQLite 或完整世界編譯，視窗再度失去回應。
- 建議修正: 將 writer 停滯設為可恢復狀態，保留現有的未確認提示。同步最新版本後，在背景開啟替代 writer，再恢復接受新寫入。

### F10 [severity: medium] [angle: code] [confidence: high] 已回覆取消的模型重載仍可被採用
- 位置: `crates/axiom-runtime/src/app.rs:2099`、`crates/axiom-runtime/src/jobs.rs:131`、`crates/axiom-runtime/src/asset_reload.rs:255`、`crates/axiom-runtime/src/asset_reload.rs:332`
- 問題: 重載會丟棄工作結果附帶的取消或逾時狀態。
- 證據: RPC 回覆 `cancelled: true` 時已設定停止旗標。`Job::poll` 會在 `Outcome::Done` 附帶 `stop`，但 `Reload::poll` 用 `Outcome::Done { value, .. }` 取值。最後一次取消檢查位於 `WorldRuntime::new` 前，建置回來後仍可產生成功結果。
- 影響: AI 在資產已開始建置後取消，下一次觀察仍可見到新模型已生效。
- 建議修正: 只允許 `stop: None` 的結果進入採用流程。對 `Cancelled` 與 `TimedOut` 回報各自的終止狀態，並測試建置完成前收到取消的情況。

### F11 [severity: medium] [angle: ai] [confidence: high] `reload_assets` 在編輯模式與 GUI 的可用性不一致
- 位置: `crates/axiom-runtime/src/app.rs:1781`、`crates/axiom-runtime/src/app.rs:1857`、`crates/axiom-runtime/src/app.rs:2112`
- 問題: 直接 RPC 的開始、監看與取消都被 Play 檢查攔截，GUI 卻能在編輯模式開始重載或啟用監看。
- 證據: `Request::ReloadAssets` 的 `match` 分支位於 `!self.editing()` 檢查之後。GUI 的 `AssetReloadAsk` 由 `poll_asset_reload` 直接交給同一個 `Reload`，中間沒有 Play 檢查。
- 影響: AI 在與人共同編輯時，使用 `reload_assets` 取消人剛啟動的工作會得到「runtime commands are available during Play preview」，即使該工作正在編輯模式運行。
- 建議修正: 在 Play 檢查前處理 `ReloadAssets`，並讓 GUI 與直接 RPC 經過同一個 host handler。加入編輯模式的開始、監看及取消測試。

### F12 [severity: medium] [angle: ai] [confidence: high] 修復外部資產後，重載無法重試同一個啟用失敗的版本
- 位置: `crates/axiom-runtime/src/app.rs:1896`、`crates/axiom-runtime/src/app.rs:1953`、`crates/axiom-runtime/src/app.rs:2144`、`crates/axiom-runtime/src/asset_reload.rs:377`
- 問題: `requested_rev` 已記住失敗的版本，例行輪詢和模型重載都無法重新建置該版本。
- 證據: `reload_after` 只在看到不同的 `requested_rev` 時排入建置。模型重載從目前生效的 runtime 建置，且 `requested_rev != rev` 會被視為 `busy`，使重載結果被標成 `superseded`。
- 影響: rev 12 因模型檔案缺失而啟用失敗、畫面仍在 rev 11 時，把檔案補回磁碟後，例行輪詢不會重試 rev 12，送出資產重載也無法讓它生效。
- 建議修正: 在啟用失敗且沒有建置中的工作時，提供對目標 revision 的顯式重試，並在診斷回覆指明該操作與 revision。

### F13 [severity: medium] [angle: human] [confidence: high] 事件交易的回滾範圍未涵蓋原生系統私有狀態
- 位置: `crates/axiom-runtime/src/world.rs:373`、`crates/axiom-runtime/src/world.rs:1414`、`crates/axiom-runtime/src/events.rs:132`
- 問題: 外掛作者可以在 `receive_events` 中修改私有狀態，但事件派送只會回滾 `RuntimeState`。
- 證據: `receive_events` 接受 `&mut self`。`step` 複製 `self.state`，再用 `self.systems.iter_mut()` 呼叫真正的系統。在某個 consumer 回傳錯誤時，程式丟棄 state 副本並保留原批次。相同合約圖的版本移轉可帶走該批未確認事件。
- 影響: 新增原生 consumer 並在 handler 更新私有計數器時，後續 consumer 的錯誤會留下該次更新。如果系統移轉保留此計數器，修復後重試待處理批次可再更新一次。現有內建 consumer 從 staging state 派送時沒有這個私有狀態問題。
- 建議修正: 明訂驗證階段只能修改 staging state，將驗證 hook 改為 `&self`。若要支援私有狀態更新，等所有 consumer 驗證成功後再執行提交 hook，並測試第二個 consumer 失敗的情境。

### F14 [severity: medium] [angle: ai] [confidence: high] Scenario 的自訂元件斷言讀到編輯值
- 位置: `crates/axiom-runtime/src/scenario.rs:348`、`crates/axiom-runtime/src/scenario.rs:362`、`crates/axiom-runtime/src/checkpoint.rs:66`、`crates/axiom-runtime/src/checkpoint.rs:147`
- 問題: `Assertion::Field` 對 transform、health 使用即時值，但 `components` 取自編譯後的 authored 記錄。
- 證據: 斷言建構 `"components": runtime.state.compiled.entities[i].components`。自訂欄位的執行期資料存在 `state.columns`，checkpoint 也從該處擷取與還原。
- 影響: 若 `game.flags.flag` 的 authored 值是 `false`、執行期欄位已更新或還原成 `true`，scenario 對 `/components/game.flags/flag` 仍可斷言 `false` 成功。
- 建議修正: 為斷言把該實體的 typed row 疊入 `components`，重用 checkpoint 的欄位轉換。加入 authored 值與即時值不同的測試。

### F15 [severity: medium] [angle: code] [confidence: high] Benchmark 將所有完整請求和回覆保留在記憶體
- 位置: `crates/axiom-runtime/src/benchmark.rs:308`、`crates/axiom-runtime/src/benchmark.rs:339`、`crates/axiom-runtime/src/benchmark.rs:395`、`crates/axiom-runtime/src/benchmark.rs:423`
- 問題: 每個 replay plan 雖有限制請求數，整套 benchmark 卻沒有 plan 數量或 transcript 總位元組上限。
- 證據: `exchange` 將完整 `request` 和 `response` 加入 `transcript`。`run` 枚舉所有 plan，將每份 transcript 放入 `results` 並保留到報告結束。回覆的序列化大小已計算，但只用作統計。
- 影響: 多套 replay plan 反覆查詢完整世界時，每次查詢的整份回覆都會累積在記憶體中。小型 suite 檔案也能產生遠大於輸入的記憶體用量。
- 建議修正: 限制每個 task 的 plan 數量，並用既有位元組計數限制整套 transcript。超出預算時保留完整統計，明確標示 transcript 已截斷。
