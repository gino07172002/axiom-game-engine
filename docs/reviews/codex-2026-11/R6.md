# R6 Audio and input — Codex review

## 摘要

- **程式正確性**：只有聲源、漏排 `audio.spatial` 的世界會在驗證時 panic。短 one-shot 也可能在模擬中完成，卻從未送到 mixer。
- **AI 可用性**：CLI 能查詢、編輯與驗證大部分音訊和輸入設定，但 `preview` 與 `verify` 可接受稍後無法啟用的音檔 revision。部分無效輸入綁定也會通過驗證。
- **人員交接**：音訊拆成事件、解碼、空間化與混音，責任大致清楚。Inspector 的音檔資訊從程序全域快取取值，可能跟目前 runtime 看到的版本不同。
- **AI–人員協作**：主要 ACL 與 editor 操作有共用 ops 和 parity 測試。音檔內容可在 revision 以外變動，而輸入情境的顯示文字修改也可能重設玩家的控制模式。

## Findings

### F1 [severity: high] [angle: code] [confidence: high] 缺少 `audio.spatial` 的純聲源世界會 panic
- 位置: `crates/axiom-core/src/audio.rs:666`
- 問題: 驗證器原本要回傳 `invalid_audio`，卻會在組出診斷前索引空陣列。
- 證據: `sources.first().map(...).unwrap_or((listeners[0].0, "audio.listener"))` 會先求值 `unwrap_or` 的參數。既有測試 `crates/axiom-runtime/tests/audio.rs:419` 移除了系統，但其 fixture 在同檔 `:43` 固定加入一個 listener。
- 影響: `preview`、`apply` 或匯入若收到只有 `audio.source`、沒有 listener 且未排入 `audio.spatial` 的世界，會觸發 panic，請求端拿不到指出缺少系統的診斷。
- 建議修正: 改用 `unwrap_or_else` 延後求值，並加一個無 listener 的回歸案例，斷言回傳 `invalid_audio`。

### F2 [severity: medium] [angle: ai] [confidence: high] `preview` 可通過稍後無法啟用的音檔變更
- 位置: `crates/axiom-core/src/audio.rs:126`、`crates/axiom-runtime/src/spatial_audio.rs:368`
- 問題: 對已被聲源引用的檔案片段，authoring 驗證無法確認檔案可讀、可解碼或符合解碼預算。
- 證據: `ClipFile::validate` 只檢查路徑長度、副檔名及 gain。`preview`、`apply` 共用的 `store.rs:285` 只執行 `World::compile`，`verify` 也在 `store.rs:606` 走編譯檢查。runtime 建立時才呼叫 `cached_clip` 讀檔解碼。
- 影響: AI 把正在使用的片段指向不存在的 `.wav`，可得到成功的 `preview` 和提交回執。之後 host 啟用失敗，`query` 已是新 revision，`observe` 仍顯示舊 runtime。
- 建議修正: 對新增或變更且已被引用的音檔，在交易外執行有界的背景檢查，讓 `preview` 回傳精確的片段欄位路徑與解碼錯誤。提交時沿用已驗證的檔案摘要，並再次核對 `expected_rev`。

### F3 [severity: medium] [angle: collab] [confidence: high] 音檔可在 revision 不變時被替換，`undo` 只還原路徑
- 位置: `crates/axiom-runtime/src/spatial_audio.rs:72`、`crates/axiom-runtime/src/spatial_audio.rs:247`
- 問題: 檔案片段的 authoring 資料沒有固定音檔內容版本。
- 證據: `resolve_files` 最後只把 canonical path 寫回 `value["file"]["path"]`。`file_key` 每次建置時重新開檔並計算 SHA-256，摘要只用於 PCM 快取。`store.rs:655` 的 `undo` 取回的是歷史 world JSON。
- 影響: 人員覆寫原路徑的 WAV 後，AI 以同一 revision 重跑 scenario 可能讀到新檔，已在執行的 editor runtime 則仍持有舊 PCM。`undo` 到舊 revision 也會從原路徑讀到新檔，歷史紀錄無法還原該次音訊變更。
- 建議修正: 為新匯入的檔案片段記錄 SHA-256。建置時優先使用同摘要的資產，缺失或摘要不符時回傳可操作的 `asset_changed` 診斷，由顯式匯入提交新摘要。

### F4 [severity: medium] [angle: code] [confidence: high] 短 one-shot 可在首次送到 mixer 前結束
- 位置: `crates/axiom-runtime/src/spatial_audio.rs:595`、`crates/axiom-runtime/src/audio.rs:247`
- 問題: 固定步進產生的音源起播狀態只保留在最新 voice snapshot，後續步進可在同一幀覆蓋它。
- 證據: `fresh` 只讓第一步保留起播時間，下一步便加上 `FIXED_DT * pitch`，到尾端就設 `playing = false` 並釋放 voice。`app.rs:1439` 每幀可跑多個固定步進，`app.rs:3060` 才呼叫一次 `audio.update` 發布最新參數。
- 影響: 允許的 `seconds = 0.01`、`pitch = 4` one-shot 若在同一幀內走完兩步，`observe` 可顯示 `finished` 增加，mixer 卻從未收到這個 token。
- 建議修正: 以有界佇列交付已獲配 voice 的 one-shot 起播事件，讓 mixer 接收後播至 PCM 結尾，並保留顯式 `stop` 的取消語意。測試應在一次輸出更新前先跑兩個固定步進，再檢查混音樣本。

### F5 [severity: medium] [angle: code] [confidence: high] 切換世界後，新 cue 會被舊序號游標略過
- 位置: `crates/axiom-runtime/src/audio.rs:84`、`crates/axiom-runtime/src/audio.rs:210`
- 問題: cue 序號的重設條件與輸出端游標的重設條件不同。
- 證據: `AudioSystem::transfer` 只在 world ID 相同時沿用 `sequence`。`Output::update` 只在 `session` 改變時把 `last` 歸零，之後只送出 `e.seq > self.last` 的 cue。`world.rs:1222` 換世界時仍沿用 `runtime_session`，另以 `runtime_epoch` 記錄換世界。
- 影響: 世界 A 已送出 200 個 cue 時，同一 host 換到世界 B 後，B 的前 200 個 cue 會被輸出端跳過。`emitted` 仍會增加。
- 建議修正: 讓輸出游標跟隨 cue 串流的世代。至少把既有 `runtime_epoch` 納入重設條件，並涵蓋移除後重新加入 `audio.events` 的同世界情況。

### F6 [severity: medium] [angle: code] [confidence: high] editor 進入 Play 時會同步讀取並雜湊音檔
- 位置: `crates/axiom-runtime/src/spatial_audio.rs:72`、`crates/axiom-runtime/src/spatial_audio.rs:107`
- 問題: 快取命中前仍要讀完整個檔案並計算 SHA-256，而 editor 的 Play 建置可在主執行緒呼叫這段工作。
- 證據: `cached_clip` 先呼叫 `file_key`，它執行 `metadata`、`File::open`、`read_to_end` 和 SHA-256，之後才查 `CLIP_CACHE`。`AudioSpatialSystem::new` 在 `:373` 對各個被引用的片段呼叫它。`app.rs:2496`、`:2534` 顯示 editor 進入 Play 時同步建立 runtime。
- 影響: 多個合法的大音檔即使已有 PCM 快取，按下 Play 仍會在主執行緒等待檔案 I/O。程式沒有為這條路徑保證 16 ms 上限，超時幅度未實測。
- 建議修正: 讓 Play 使用現有的背景 runtime 建置流程。音檔準備以片段計數回報進度，在檔案之間檢查取消，完成後再切換 runtime。

### F7 [severity: medium] [angle: code] [confidence: high] pack 音檔解析在片段數量預算生效前執行
- 位置: `crates/axiom-runtime/src/spatial_audio.rs:211`、`crates/axiom-core/src/audio.rs:408`
- 問題: `MAX_LIBRARY_CLIPS` 能拒絕超量的 pack，但無法及早擋住它的音檔 I/O。
- 證據: `resolve_files` 逐筆呼叫 `cached_clip`，進入迴圈前沒有數量檢查。`package.rs:535` 先跑 package resolver，`package.rs:389` 才編譯合成後的世界並執行 `AudioLibrary::validate`。
- 影響: pack 可以宣告超過 64 個片段並全部指向同一個合法的大 WAV。匯入會對各項重複讀檔和雜湊，最後才以片段超量拒絕。
- 建議修正: 在 resolver 開啟第一個檔案前，用 `MAX_LIBRARY_CLIPS` 檢查 `clips.len()`，並在 `/resources/audio.library/clips` 回報超量診斷。保留合成後的預算檢查，以涵蓋多 pack 合併。

### F8 [severity: medium] [angle: collab] [confidence: high] `apply` 可建立 ACL 與 Input Map 拒絕的同名按鈕和軸
- 位置: `crates/axiom-core/src/ir.rs:748`、`crates/axiom-core/src/registry.rs:281`
- 問題: `input.bindings` 資源驗證沒有檢查 `buttons` 和 `axes` 的 action 名稱是否重複。
- 證據: 兩張表分別反序列化，registry 只檢查數量、長度及 gamepad 綁定。共用的 `edit_input` 在 `ops_tuning.rs:189` 與 `:204` 會拒絕同名異類。`world.rs:25` 先將軸值寫入 `ActionMap`，再用同名按鈕值覆寫。
- 影響: AI 用 `apply` 提交兩個同名 `move` 後，玩家按住軸的方向鍵時，未按下的同名按鈕仍會把該軸值覆寫為零。人員透過 editor 嘗試重綁時，還會遇到共用 ops 的類型錯誤。
- 建議修正: 在 `InputBindings` 的共用驗證拒絕重複 action，指出兩個 JSON 路徑。讓 `input remove` 能在同一筆編輯清掉既有資料的兩筆同名綁定。

### F9 [severity: medium] [angle: collab] [confidence: high] 修改 context 標籤會重設玩家當前控制模式
- 位置: `crates/axiom-runtime/src/input.rs:87`、`crates/axiom-runtime/src/input.rs:132`
- 問題: 熱重載是否保留 `active` 和 `held`，取決於整份 `Config` 是否相等。
- 證據: `Contexts::new` 用 `initial` 建立 `active` 並清除 `held`。`transfer` 只在 `self.config == old.config` 時複製兩者，而 `ContextDef` 的相等比較包含 `label`。
- 影響: 人員在即時 host 控制小隊時，AI 只修正小隊 context 的顯示名稱，revision 啟用後仍會切回 `initial`，同時改變輸入路由、相機或指標捕捉。
- 建議修正: 只要舊 `active` ID 仍存在，就保留該 ID 和 `held`，並使用新定義的路由。舊 ID 被移除時才回到 `initial`。

### F10 [severity: medium] [angle: code] [confidence: high] 極短 WAV 以高 pitch 循環時會永久靜音
- 位置: `crates/axiom-runtime/src/audio_mix.rs:284`、`crates/axiom-runtime/src/audio_mix.rs:301`
- 問題: mixer 的循環位置每個樣本最多減去一次片段長度。
- 證據: `v.pos += step` 後只執行一次 `v.pos -= len as f64`。下一次迭代若索引仍超界，就把 `live` 設為 `false`。`audio_file.rs:227` 接受任何至少一個 frame 的 WAV，而 `audio.rs:494` 允許 `pitch = 4`。
- 影響: 一個 22,050 Hz、單 frame 的 WAV 以四倍速循環時，第一個輸出樣本後位置變成 `3`。mixer 隨即停聲，同 token 的後續參數也不會重新啟動它。模擬仍可回報 `playing: true`。
- 建議修正: 循環越界時對片段長度取模，並以單樣本 PCM、`pitch = 4` 測試連續兩個 buffer。

### F11 [severity: medium] [angle: code] [confidence: high] XInput 空槽探測集中在同一個主執行緒幀
- 位置: `crates/axiom-runtime/src/gamepad.rs:188`、`crates/axiom-runtime/src/gamepad.rs:230`
- 問題: 空槽探測降頻了，但首次探測及後續重試會集中執行，仍受同步裝置呼叫時間限制。
- 證據: 四槽 `probe` 初始皆為 `None`。`poll` 在同一個迴圈同步呼叫 `XInputGetState`，並用同一個 `started + PROBE_INTERVAL` 排定所有空槽的下次探測。模組註解也明示空槽查詢較慢。
- 影響: 沒有連接手把時，首幀和之後每秒都有一幀要等四次空槽查詢。程式碼可確認查詢會集中，是否超過 16 ms 尚未量測。
- 建議修正: 把 XInput 輪詢移到有界、可停止的背景工作，主執行緒每幀只取最新 `Pads` 快照。沿用 `poll_us_last` 和 `poll_us_max` 量測變更前後耗時。

### F12 [severity: low] [angle: ai] [confidence: high] 不可匹配的鍵名可通過 CLI 驗證
- 位置: `crates/axiom-core/src/registry.rs:281`、`crates/axiom-core/src/ops_tuning.rs:94`
- 問題: `apply` 只限制鍵名字串長度，ACL 的 `valid_key_name` 則只驗證字元形狀，兩者都未完整核對 native host 能產生的鍵名。
- 證據: `input.bindings` 的 registry validator 允許在鍵盤欄位填 `PadA`，但 `edit_input` 在 `ops_tuning.rs:135` 明確要求這個值走 `input pad`。任意符合形狀的英數字串則可通過 `valid_key_name`。`world.rs:25` 以字串做精確比對，`app.rs:1427` 從實體 `KeyCode` 產生鍵名字串。
- 影響: AI 可以成功提交鍵盤永遠無法觸發的綁定。直接對 action 注入數值的 scenario 仍可能通過，掩蓋 native 輸入失效。
- 建議修正: 讓資源驗證和 `edit_input` 共用 canonical 鍵名清單，涵蓋實際支援的 `KeyCode` 與滑鼠、滾輪名稱。診斷應標出欄位路徑，對 `PadA` 這類值提示 `input pad`。

### F13 [severity: low] [angle: human] [confidence: high] Inspector 可能顯示同一路徑的舊音檔資訊
- 位置: `crates/axiom-runtime/src/spatial_audio.rs:118`、`crates/axiom-runtime/src/spatial_audio.rs:189`
- 問題: `file_info(path)` 從整個程序的 PCM 快取依路徑取第一筆，無法判斷哪一筆屬於目前 runtime。
- 證據: `CLIP_CACHE` 以內容雜湊排序，`file_info` 用 `.find(|f| f.path == path)`。檔案內容變更後，新舊項目可以並存。相同內容從另一個路徑載入時，`found` 也只改回傳的 `FileInfo` 副本。Inspector 在 `editor/mod.rs:1522` 讀這個 helper，`observe` 則從 runtime 自己的 `Clip.file` 取資料。
- 影響: 同一路徑的 WAV 從一秒替換成兩秒並熱重載後，Inspector 可能仍顯示一秒，而 CLI `observe` 已回報兩秒。相同內容的第二個路徑也可能查不到資訊。
- 建議修正: 讓 Inspector 依 clip ID 從目前作用中的 runtime 讀取 `FileInfo`，並用 runtime revision 標示該筆資料。尚未啟用的片段顯示待載入狀態。
