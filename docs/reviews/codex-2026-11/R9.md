# R9 Packaging and player executable — Codex review

## 摘要

程式正確性：優先修正暫存目錄與輸出替換的資料遺失風險，其次是檔案複製上限、取消時機和 player 的路徑邊界。  
AI 可用性：CLI 可直接執行 `package`，也可透過 `discover editor_commands` 找到 `file.build_game` 並用 `observe` 或 `observe_delta` 查進度。`preview`、`verify` 和 scenarios 驗證的是 authoring world 或其模擬，無法確認實際的出貨目錄。  
人工接手：CLI 與 GUI 共用封裝函式。`game.json` 的寫入與讀取規則分散在兩端，素材路徑的判定也依賴未標記型別的 JSON 字串。  
AI 與人協作：封裝以磁碟上的 pack 為來源。建置結果缺少來源指紋及可用來核對編輯器 revision 的資訊。

## Findings

### F1 [severity: high] [angle: code] [confidence: high] 固定暫存目錄可刪除來源 pack 或另一個建置的檔案
- 位置: `crates/axiom-runtime/src/packaging.rs:92`、`crates/axiom-runtime/src/packaging.rs:109`、`crates/axiom-runtime/src/packaging.rs:122`
- 問題: 來源重疊檢查只涵蓋最終輸出路徑。
- 證據: `package` 將暫存目錄固定為輸出目錄的同層 `<out>.partial`。只要該目錄存在，就呼叫 `remove_dir_all`。建置失敗也會刪除同一路徑。
- 影響: 若來源 pack 目錄正好是 `Game.partial`、輸出是同層的 `Game`，來源通過初步驗證後會被刪除。CLI 與編輯器同時建置到同一個位置，也會共用並清理彼此的暫存目錄。
- 建議修正: 以 `create_dir` 原子建立每次建置專用的唯一同層暫存目錄。只清理本次成功建立的目錄，並加入來源目錄名稱以 `.partial` 結尾的回歸測試。

### F2 [severity: high] [angle: code] [confidence: high] 發佈前會無條件刪除新出現的輸出目錄
- 位置: `crates/axiom-runtime/src/packaging.rs:97`、`crates/axiom-runtime/src/packaging.rs:127`
- 問題: 替換決策與實際刪除之間隔著整次建置，刪除後的發佈也沒有復原步驟。
- 證據: 開始時僅在 `out.exists()` 為真時檢查 `force` 和 `game.json`。完成時只要 `out.exists()` 為真，就直接 `remove_dir_all(&out)`，再以 `rename` 發佈。
- 影響: 沒有指定 `--force` 時，建置期間由另一個程序建立的同名目錄仍會被刪除。指定 `--force` 時，若刪除成功後 `rename` 失敗，上一版成品已經消失。
- 建議修正: 一般發佈使用會拒絕覆蓋既有目的地的操作。強制替換在同一輸出鎖下重新驗證目標，先將舊目錄移到備份位置，發佈失敗時移回，成功後才清理備份。

### F3 [severity: high] [angle: code] [confidence: high] 4 GiB 上限在整檔載入及寫出後才檢查
- 位置: `crates/axiom-runtime/src/packaging.rs:173`、`crates/axiom-runtime/src/packaging.rs:185`、`crates/axiom-runtime/src/packaging.rs:266`
- 問題: 複製單一檔案所需的記憶體等於整個檔案大小，且總量限制漏算最後複製的 player。
- 證據: `copy_hashed` 以 `std::fs::read` 整檔讀入，再 `write` 並計算 SHA-256。內容檔回傳後才檢查 `MAX_BYTES`，player 加入 `bytes` 後沒有再檢查。
- 影響: 大型素材可能讓內嵌建置 worker 的編輯器程序因配置失敗而終止，也可能先寫出超過限制的暫存檔。內容接近 4 GiB 時，加上 player 後仍可能回報成功。
- 建議修正: 以固定大小的緩衝區串流複製及雜湊。每次寫入前扣除剩餘預算，並對內容、player 和 `game.json` 套用同一上限。

### F4 [severity: medium] [angle: code] [confidence: high] Player 啟動時只做字面路徑檢查
- 位置: `crates/axiom-player/src/main.rs:64`、`crates/axiom-player/src/main.rs:150`
- 問題: 啟動時未驗證 `pack` 解析後的位置，也未套用封裝端對外部素材的限制。
- 證據: `read_game` 只要求 `pack.components()` 全為 `Component::Normal`，隨後回傳 `dir.join(pack)`。`run` 直接把這個路徑交給 `ContentPackage::load`。該載入器會以解析後的 pack 作為邊界，並允許 authoring 的 `animation.library` 使用 `external: true`。
- 影響: 如果遊戲目錄內的 `content` 是指向外部的目錄連結，player 會載入連結目的地。被修改的 pack 也能讓 player 嘗試載入遊戲目錄外的動畫素材，搬移後可能啟動失敗。
- 建議修正: 啟動時解析遊戲目錄和 pack 的實際路徑並驗證包含關係，再與 packager 共用出貨模式的素材限制。補上目錄連結與外部動畫引用測試。

### F5 [severity: medium] [angle: code] [confidence: high] 取消或 watchdog 逾時後仍可能發佈
- 位置: `crates/axiom-runtime/src/packaging.rs:74`、`crates/axiom-runtime/src/packaging.rs:190`、`crates/axiom-runtime/src/packaging.rs:199`、`crates/axiom-runtime/src/packaging.rs:127`、`crates/axiom-runtime/src/editor/build.rs:205`、`crates/axiom-runtime/src/editor/build.rs:272`
- 問題: 最後一次取消檢查早於成品驗證及發佈，且前置驗證、目錄掃描和整檔 I/O 缺少取消檢查點。
- 證據: packager 在複製 player 後檢查旗標，接著重新載入 staging、掃描路徑並發佈，中間未再檢查。編輯器 watchdog 設旗標後，可以先將 worker 標為 `abandoned`。
- 影響: 若驗證停住超過 grace period，使用者可能先看到工作已放棄，稍後該 worker 恢復並替換正式輸出。
- 建議修正: 在掃描、串流複製與驗證階段加入取消檢查點。在發佈鎖內、任何替換前再次檢查旗標，並將開始發佈定為明確的取消截止點。更新 `build.rs:235` 的註解，使其與實際截止點一致。

### F6 [severity: medium] [angle: code] [confidence: high] 封裝成功仍可能缺少 glTF 的必要附屬檔
- 位置: `crates/axiom-runtime/src/packaging.rs:147`、`crates/axiom-runtime/src/packaging.rs:199`、`crates/axiom-runtime/src/packaging.rs:342`
- 問題: 成品驗證能確認動畫主檔路徑，卻未檢查動畫匯入器稍後會讀取的附屬檔。
- 證據: `build` 套用 `excludes` 後，只用 `ContentPackage::load` 和 `escapes` 驗證 staging。`referenced_files` 收集 manifest、world、宣告素材、shader 和解析後的絕對路徑，未展開 glTF buffer 或 image URI。
- 影響: 保留 `.gltf`、排除它引用但未列在 manifest 的 `.bin` 時，`package` 可回報成功。player 建立 `animation.evaluate` 系統時才會因缺少 buffer 而啟動失敗。
- 建議修正: 重用動畫匯入器的依賴解析，在 staging 驗證必要的附屬檔，並將缺少的檔案與來源素材寫入錯誤。加入排除必要 `.bin` 的回歸測試。

### F7 [severity: medium] [angle: human] [confidence: high] `game.json` 的產生端與讀取端使用不同的有效值規則
- 位置: `crates/axiom-runtime/src/packaging.rs:80`、`crates/axiom-runtime/src/packaging.rs:196`、`crates/axiom-player/src/main.rs:115`、`crates/axiom-player/src/main.rs:138`
- 問題: 維護者需要同時掌握兩組約束，packager 可產生 player 立即拒絕的描述檔。
- 證據: packager 直接寫入 `manifest.id`，對 title 只檢查去除空白後是否為空。player 只接受 ASCII 英數及 `-_.` 的 ID，並限制整份 `game.json` 為 64 KiB。核心 package loader 採用的通用 ID 驗證允許 Unicode 英數及 `/`。
- 影響: 通過內容驗證且 ID 含 Unicode 字母的 pack 可成功封裝，雙擊成品時卻會收到 `game.json` ID 錯誤。
- 建議修正: 共用型別化的 `GameManifest` 與序列化驗證，在建立暫存目錄前執行同一組 ID、title 及大小檢查。加入 packager 輸出經 player 解析的契約測試。

### F8 [severity: medium] [angle: collab] [confidence: high] 建置結果無法對照已審核的內容
- 位置: `crates/axiom-runtime/src/editor/build.rs:115`、`crates/axiom-runtime/src/editor/build.rs:144`、`crates/axiom-runtime/src/editor/build.rs:238`、`crates/axiom-runtime/src/editor/build.rs:304`
- 問題: 編輯器預設以目前 world 的 title 命名，實際內容來自磁碟上的 pack。成功回報沒有可核對的來源版本。
- 證據: `build_command` 從 `self.world.title` 取預設值，`start_build` 將 `self.build.pack` 傳給 worker。可觀察的 `last` 只有輸出、檔數、大小、時間及取消狀態。完整雜湊報告存於 `last_report`，`build_observation` 未公開它或其摘要指紋。
- 影響: AI 在 revision R 提交變更後，人員可看到新 title 並成功建置，但成品的 gameplay 仍來自舊 pack。兩人無法從完成回報確認成品是否包含剛審核的變更。資料庫的 `undo` 也只會還原 authoring revision。
- 建議修正: 在完成回報加入實際封裝的 pack 指紋、輸出識別及當時的 editor revision，明確標示後者僅供參考。提供 `expected_pack_digest` 供 CLI 與編輯器建置共同核對已審核的 pack。

### F9 [severity: medium] [angle: ai] [confidence: high] Build 指令會默默採用錯誤型別欄位的預設值
- 位置: `crates/axiom-runtime/src/editor/build.rs:115`
- 問題: 指令只驗證參數是 JSON object，欄位拼錯或型別錯誤不會得到診斷。
- 證據: `out` 和 `title` 以 `as_str().map_or_else(...)` 解析，`force` 以 `as_bool().unwrap_or(false)` 解析。程式未檢查未知欄位。
- 影響: AI 傳入 `{"output":"D:/staging/review"}` 時，指令可成功啟動，卻寫到預設的 `dist/<title>`。傳入字串形式的 `force` 時，也只會在碰到既有輸出後收到與真正輸入錯誤無關的訊息。
- 建議修正: 用具名 `Deserialize` struct、optional 欄位及 `deny_unknown_fields`，回報錯誤欄位與預期型別。在啟動 worker 前拒絕無效參數。

### F10 [severity: medium] [angle: code] [confidence: high] 檔數預算未限制目錄走訪或排除清單
- 位置: `crates/axiom-runtime/src/packaging.rs:216`、`crates/axiom-runtime/src/packaging.rs:212`
- 問題: 遞迴深度、走訪項目數及 `skipped` 回應長度都沒有上限。
- 證據: `collect` 將每層 `read_dir` 全部收進 `Vec`，遞迴進入每個未排除的子目錄，並保留每個排除項目的路徑。只有將保留檔推入 `out` 時，才檢查 `MAX_FILES`。
- 影響: 只有少量成品檔的 pack，仍可因大量空目錄或被排除的檔案而耗費大量走訪時間和記憶體。排除項目也能產生遠超過成品檔數的 JSON 回應。
- 建議修正: 改用有界的迭代走訪，對所有走訪項目及深度計數。報告預設回傳排除總數及有限筆範例，完整清單由明確選項取得。

### F11 [severity: medium] [angle: code] [confidence: high] Smoke test 等待子程序沒有 watchdog
- 位置: `scripts/package-smoke-test.ps1:29`、`scripts/package-smoke-test.ps1:53`
- 問題: 封裝和 player 的等待都沒有牆鐘時間上限。
- 證據: `Invoke-Package` 同步呼叫 `$cli`。player 使用 `Start-Process -Wait -PassThru`，`Stopwatch` 只在程序退出後記錄耗時。
- 影響: player 若卡在啟動或 GPU 初始化，`--smoke-frames` 尚未開始計數，測試會持續等待，後續 pack 和負面案例都無法執行。
- 建議修正: 對兩個子程序使用有上限的 `WaitForExit`。逾時時終止本次啟動的程序、限時回收，並回報 pack 名稱、階段和日誌路徑。

### F12 [severity: medium] [angle: human] [confidence: high] 素材邊界掃描會把一般內容文字當成檔案
- 位置: `crates/axiom-runtime/src/packaging.rs:273`、`crates/axiom-runtime/src/packaging.rs:312`、`crates/axiom-runtime/src/packaging.rs:411`
- 問題: 素材引用的判定依賴字串外觀，無法從欄位用途判斷該值是否會被讀取。
- 證據: `absolute_strings` 和 `escapes` 遞迴讀取所有 JSON 字串。只要字串可解讀成絕對路徑，且 `canonicalize` 失敗或解析後越界，就會列為外部引用。
- 影響: 作者把 Windows 路徑當作畫面上的教學文字時，即使遊戲從未讀取該路徑，封裝也會拒絕並要求搬動該檔案。錯誤沒有指出是哪個內容欄位觸發。
- 建議修正: 由既有素材 resolver 提供帶欄位位置的檔案引用，封裝檢查和報告都使用這份清單。加入含絕對路徑文字的 UI 文件測試。

### F13 [severity: low] [angle: ai] [confidence: high] 檔案雜湊報告漏掉 `game.json`
- 位置: `crates/axiom-runtime/src/packaging.rs:185`、`crates/axiom-runtime/src/packaging.rs:196`、`crates/axiom-runtime/src/packaging.rs:212`
- 問題: 報告裡的 `files`、SHA-256 和 `bytes` 未涵蓋決定 player 啟動設定的 `game.json`。
- 證據: `files` 與 `bytes` 在複製內容及 player 時更新。`game.json` 另外透過 `std::fs::write` 寫入，未加入統計。
- 影響: 固定 `--exe-name`、只改 `--title` 時，兩次成品的檔案雜湊清單仍可完全相同，但 player 顯示的視窗標題不同。只比對清單的自動化無法察覺變動。
- 建議修正: 對同一份序列化位元組計算 `game.json` 的長度及 SHA-256，將它納入成品清單和總量。

### F14 [severity: low] [angle: code] [confidence: high] Smoke test 可能漏掉成品檔案被覆寫或素材路徑仍指向舊位置
- 位置: `scripts/package-smoke-test.ps1:46`、`scripts/package-smoke-test.ps1:67`、`scripts/package-smoke-test.ps1:69`
- 問題: 腳本驗證了檔名集合與一個禁止出現的路徑前綴，卻未驗證檔案內容及素材實際解析位置。
- 證據: 啟動前後只比對 `FullName`。資料庫及 WAL 被當作文字讀取，僅搜尋 repo 的 `content` 路徑。
- 影響: player 若覆寫同名成品檔，檔名比對仍會通過。若資料庫指向仍存在的原始 `dist` 副本，路徑也不符合腳本搜尋的 repo `content` 前綴。
- 建議修正: 比較啟動前後的相對路徑與 SHA-256。透過 `axiom query` 檢查測試素材的解析路徑確實位於搬移後的 `content` 目錄，並在啟動前移開原始輸出以驗證獨立性。

### F15 [severity: low] [angle: ai] [confidence: high] 缺少 `APPDATA` 時，錯誤建議的 `--db` 無法恢復啟動
- 位置: `crates/axiom-player/src/main.rs:49`、`crates/axiom-player/src/main.rs:163`
- 問題: 指定資料庫也會先走 `APPDATA` 的必經路徑。
- 證據: `run` 在比對 `args.db` 前就執行 `data_dir(&game.id)?`。`data_dir` 在 `APPDATA` 為空或不存在時報錯，並建議 `pass --db PATH`。
- 影響: 自動化環境照訊息提供 `--db` 後，player 仍在同一步退出。
- 建議修正: 只有採用預設資料庫時才要求 `APPDATA`。有 `--db` 時，以指定位置選擇 crash log 的目錄，並測試無 `APPDATA` 的啟動參數分支。
