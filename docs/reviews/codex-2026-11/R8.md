# R8 Editor — Codex review

## 摘要

一般程式碼方面，背景寫入已分離部分重工作，但 Hierarchy、Graphs、偏好儲存與錄影結束仍有同步路徑。  
AI 操作方面，多數內容編輯可透過 ACL 完成，但部分 `editor_view` 命令會把失敗回成成功，草稿合併也有無法從 CLI 進入的路徑。  
人類交接方面，共用 ops 與 parity tests 提供了修改起點。命令註冊、寫入分類與 Play 限制分散，新增命令時容易漏接。  
AI 與人類協作方面，`expected_rev` 能防止直接覆蓋較新的 revision，但提交確認前清除草稿，以及替其他使用者送出草稿，會破壞復原與稽核。

## Findings

### F1 [severity: high] [angle: collab] [confidence: high] Inspector 在交易成功前清除復原所需的草稿
- 位置: `crates/axiom-runtime/src/editor/mod.rs:909`
- 問題: 背景暫存結果先出現在畫面上時，Inspector 可以在資料庫確認提交前丟失原始草稿。
- 證據: `apply_staged` 依 `live_inspector && busy` 決定是否呼叫 `reset_draft()`。`ui.rs:1680` 將 Live 編輯加入 `actions` 後立即呼叫 `draft.mark_committed()`，而 `mod.rs:249` 會移動基準並清除 dirty flags。`mod.rs:967` 的 `revert_staged` 恢復已提交世界後也直接重設草稿。
- 影響: 人類送出的編輯已顯示為暫存結果，AI 隨後搶先提交。資料庫拒絕舊 `expected_rev` 時，人類原本的編輯可能已無法使用 Copy JSON 或 Merge 找回。
- 建議修正: 為每筆待提交的 Inspector 寫入保留草稿與基準，收到成功回執後再丟棄。遇到 revision 衝突時，還原成可複製或合併的 stale draft。

### F2 [severity: high] [angle: collab] Merge 提前清除草稿，而且空結果跳過過期檢查
- 位置: `crates/axiom-runtime/src/editor/merge.rs:316`
- 問題: 草稿合併在確認結果仍有效或提交成功前，就可能清除草稿與使用者選定的解法。
- 證據: `poll_merge` 在背景工作回傳空 edits 時直接 `close_merge()` 和 `reset_draft()`。只有非空 edits 會進入 `take_merge_write` 的 `merge_outdated()` 檢查。該檢查通過後，`merge.rs:363` 也會在送出 `Action::Write` 的當下清空草稿並顯示已提交。
- 影響: 背景工作算出「目前值已包含草稿」，但 AI 在期間再次修改同一欄位時，舊結果仍能清除草稿。非空合併也可能在送出後遇到 CAS 衝突，此時人類已失去原草稿與合併選項。
- 建議修正: 讓空與非空結果共用 revision、草稿指紋及佇列檢查。非空合併收到成功回執後才清除草稿。補上背景工作期間 revision 更新，以及送出後 CAS 失敗的測試。

### F3 [severity: medium] [angle: collab] AI 開啟另一張 Graph 會替人類提交草稿
- 位置: `crates/axiom-runtime/src/editor/graph.rs:1451`
- 問題: 遠端 `graph.open` 看起來是切換檢視，卻可以送出目前人類尚未完成的內容編輯。
- 證據: 切換 graph 會呼叫 `graph_flush()`。`graph.rs:1387` 把 dirty element 或 rule 轉成寫入，`graph.rs:1769` 再把 `graph.queued` 當成當前命令的 actions 回傳。`mod.rs:2267` 的 dirty 檢查沒有 Graph 草稿。Host 以 `Agent` 作為 bridge 命令所送寫入的作者。
- 影響: 人類還在編輯 FSM state 時，AI 開啟另一個 machine，可能產生一筆包含人類未完成編輯、作者卻標成 `Agent` 的 revision。
- 建議修正: 遠端切換 Graph 前檢查該面板的 dirty 草稿，以結構化錯誤請操作者先完成或取消。加入經由 bridge 驗證 revision 和作者的測試。

### F4 [severity: medium] [angle: collab] UI Editor 在任何世界更新時捨棄正在輸入的內容
- 位置: `crates/axiom-runtime/src/editor/ui_editor.rs:451`
- 問題: UI 文件的快取更新也會無條件清除 widget 與 effect 草稿。
- 證據: `ui_editor_tab` 用 `(self.rev, self.world_version)` 當快取鍵。快取重建時將 `effect_draft` 和 `widget_draft` 設為 `None`。`ui_editor.rs:1124` 則等指標釋放且焦點清除後才將 widget 草稿轉為寫入。
- 影響: 人類在 UI Editor 輸入時，AI 只要提交一次無關的物件改名，下一次重建預覽就會捨棄尚未送出的輸入。
- 建議修正: 快取重建時依 widget 或 effect ID 比對草稿的基準值。目標未變時保留草稿，目標已變時保留內容並標示衝突。

### F5 [severity: medium] [angle: collab] `shader.draft` 可直接取代人類未儲存的 WGSL
- 位置: `crates/axiom-runtime/src/editor/shader_editor.rs:135`
- 問題: Shader 有自己的 dirty 狀態，但遠端草稿替換沒有以該狀態作為保護。
- 證據: `shader_editor.rs:62` 以 `draft != base` 公開 shader 的 dirty 狀態。`mod.rs:2267` 的 `Editor::dirty()` 只檢查 entity、resource、material 和 prefab。`shader_draft_command` 完成參數驗證後直接執行 `self.tuning.shader.draft = source`。
- 影響: 人類在 Shader source 欄位有尚未 Apply 的內容時，AI 若送出 `shader.draft` 來檢查另一版 WGSL，就能清掉人類的輸入，History 也沒有可取回的 revision。
- 建議修正: 在替換前檢查 shader 草稿是否已修改，預設回傳 `editor_dirty`。需要遠端替換時，要求呼叫端提供它所觀察到的草稿指紋。

### F6 [severity: medium] [angle: ai] 部分 `editor_view` 命令把參數錯誤回成成功
- 位置: `crates/axiom-runtime/src/editor/commands.rs:1200`
- 問題: 命令錯誤只顯示在 GUI，CLI 呼叫端收到的卻是成功。
- 證據: `run_command_with` 用 `Ok(...)` 包住 `ui_command` 與 `run_with_arg` 的回傳值。`ui_editor.rs:335` 遇到不存在的 widget 時呼叫 `set_error` 後回傳空 actions。`world_panel.rs:528` 遇到無效的 `object.camera_blocker` 參數也只呼叫 `set_error`。Host 在命令成功且沒有待處理寫入時直接回傳 `ok: true`。
- 影響: CLI 對不存在的 widget 執行 `ui.select` 後，會看到成功回覆，可能接著對仍停留在畫面上的舊 widget 操作。
- 建議修正: 讓這兩個 handler 回傳 `Result<Vec<Action>>` 並傳遞原始診斷。只有有效的無變更操作回傳成功與空 actions。用 CLI 測試區分兩種情況。

### F7 [severity: medium] [angle: ai] CLI 無法操作 discovery 公開的 stale draft 合併
- 位置: `crates/axiom-runtime/src/editor/mod.rs:1932`
- 問題: 進入遠端命令的 dirty 檢查，會攔住正是為 dirty draft 設計的合併命令。
- 證據: `commands.rs:621` 註冊 `merge.open proposal:N|draft`，`commands.rs:2019` 將 `merge.open`、`merge.pick`、`merge.commit` 列為 `editor_view` 命令。Host 會先呼叫 `remote_view`，即使沒有選取、聚焦或切換面板，`remote_view` 仍要求 `!self.dirty()`。GUI 的 `ui.rs:1845` 直接呼叫 dispatcher，能走到合併。`coedit_tests.rs:383` 也直接測 dispatcher。
- 影響: 人類請 AI 協助處理 GUI 上的 stale Inspector draft 時，CLI 會要求先 Apply 或 Reload。前者受 stale 檢查阻擋，後者會清掉待合併內容。
- 建議修正: 只在請求包含會改動選取或 Inspector 的欄位時套用通用 dirty 檢查。讓合併命令使用自己的前置條件，並補一個實際 `editor_view` 路徑的測試。

### F8 [severity: medium] [angle: code] Hierarchy 只虛擬化繪製，每幀仍重建整棵樹
- 位置: `crates/axiom-runtime/src/editor/ui.rs:772`
- 問題: 即使世界、搜尋與展開狀態都沒有變，Hierarchy 仍在主執行緒配置並重建資料。
- 證據: 每次繪製都呼叫 `Hierarchy::new(&self.world)`，建立新的 `rows`，再掃描全部物件或重走展開的樹。`ui.rs:826` 還會複製 flags 並重新求繼承結果。`show_rows` 到 `ui.rs:856` 才限制可見列的排版工作。
- 影響: 大場景即使只顯示十幾列，閒置畫面的成本仍會隨物件、關聯與場景成員數增加。
- 建議修正: 以 `world_version` 快取階層索引，依搜尋、場景和摺疊狀態更新列清單。只有階層或 flags 改變時才重算繼承結果。

### F9 [severity: medium] [angle: code] 修改 Graph 的單一節點會在主執行緒複製完整 World
- 位置: `crates/axiom-runtime/src/editor/graph.rs:1338`
- 問題: Graph 為同幀操作建立暫存狀態時，同步複製與編輯整個世界。
- 證據: `graph_write` 執行 `self.graph_world().clone()`，逐筆複製並套用 edits，再將 `next` 存入 `graph.scratch`。雙擊新增帶座標的 state 時，`graph.rs:1528` 先為節點位置複製一次 `World`，之後仍進入 `graph_write`。
- 影響: 在大型關卡調整一個 FSM state 時，工作量會受無關的物件與資源大小影響。雙擊新增 state 的單次互動會走到兩次完整複製。
- 建議修正: 同幀 Graph 暫存只保留受影響的 graph 或 rule 資源，依原順序產生同一批 edits。完整 `World` 的暫存與驗證交給現有背景寫入流程。

### F10 [severity: medium] [angle: code] 偏好每幀序列化，寫入失敗後同一內容也不會重試
- 位置: `crates/axiom-runtime/src/editor/commands.rs:1789`
- 問題: 偏好存檔把序列化與檔案 I/O 放在繪製路徑，並把失敗的內容標記成已儲存。
- 證據: `ui.rs:249` 在指標按鈕未按下的每一幀呼叫 `save_prefs()`。`save_prefs` 先對整份 `Prefs` 執行 `to_string_pretty`，才比較是否有變更。變更時直呼 `std::fs::write`，而 `Err` 分支也設定 `prefs_saved = Some(text)`。
- 影響: 閒置畫面持續配置序列化字串。若儲存遇到暫時性檔案鎖，解鎖後相同內容仍會被跳過，重啟後可能讀回舊版或不完整的偏好。
- 建議修正: 以偏好變更旗標觸發合併儲存，在單一背景工作中先寫暫存檔再替換。成功後才更新已儲存標記，失敗則保留待存狀態。

### F11 [severity: medium] [angle: code] 結束錄影會同步驗證並刷寫 scenario 檔
- 位置: `crates/axiom-runtime/src/editor/record.rs:437`
- 問題: 停止錄影時，Host 直接在主執行緒執行整份 scenario 的輸出流程。
- 證據: `Recorder::finish` 呼叫 `scenario()` 逐筆序列化輸入與命令，再用 `serde_json::from_str::<Scenario>` 解析完成的文字。接著建立目錄與檔案，並執行 `write_all` 和 `sync_all`。Host 在停止錄影或 Play 的路徑直接呼叫它。
- 影響: 停止長錄影時，GUI 必須等完整轉換、驗證與磁碟同步完成。即使檔案有 1 MiB 上限，這條路徑仍無法靠該上限保證 16 ms。
- 建議修正: 在錄影結束時移交 recorder 與必要的結束狀態，將序列化、驗證及檔案輸出放進有逾時的背景工作，透過現有 job 觀測回報結果。

### F12 [severity: medium] [angle: code] 模型熱重載後，已顯示的縮圖可繼續使用舊內容
- 位置: `crates/axiom-runtime/src/editor/thumbs.rs:85`
- 問題: 縮圖的記憶體鍵只反映路徑與匯入選項，同路徑的新檔案內容不會使已上傳的縮圖失效。
- 證據: 模型 `signature` 是 `path` 和 `options`，`thumbs.rs:179` 對該字串計算 `ThumbKey`。`thumbs.rs:374` 只為缺少狀態或 `OnDisk` 的項目排工作。`reload.rs:14` 只通知 Host 重載模型，成功採用時也沒有通知 Editor 使縮圖失效。
- 影響: 原地更新 GLB 後執行 `asset.reload`，Scene 能顯示新模型，Assets 卻可能繼續顯示舊縮圖，讓操作者無法單憑瀏覽器確認資產版本。
- 建議修正: 成功重載後，以變更的來源路徑使模型與相依 prefab 的縮圖失效。讓下一次可見請求沿用現有背景雜湊和重建流程。

### F13 [severity: low] [angle: human] 新增命令時須同步維護獨立的寫入分類
- 位置: `crates/axiom-runtime/src/editor/commands.rs:648`
- 問題: 命令表與 Play 寫入限制各自手填，現有命令已顯示兩者會分歧。
- 證據: `commands.rs:482` 註冊 `ui.place`，`ui_editor.rs:328` 將它轉成 ACL 編輯，`ui_editor.rs:382` 再走 `op_write`。但 `ui.place` 不在 `CONTENT_COMMANDS`。`commands.rs:932` 只依該表施加通用 Play 限制，而 `commands.rs:1098` 對 `ui.place` 只檢查 `busy`。
- 影響: 維護者只新增 registry 項目和 handler 時，命令可在 Play 被列為可用，直到 Host 拒絕寫入才顯示原因。
- 建議修正: 將是否寫入內容放進 `Command` 定義，讓 Play 限制直接讀取同一筆資料。以 `ui.place` 加一個 Play 可用性測試。

## 未涵蓋

結論來自靜態閱讀。Editor 目錄已全域掃描，並追讀了與 findings 有關的實作、測試和 Host 呼叫點。其餘面板與測試未逐行驗證，scope 外的 crate 僅用於確認呼叫語意。未執行 GUI、CLI、測試或效能量測，未修改任何檔案。
