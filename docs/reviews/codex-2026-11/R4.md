# R4 Animation — Codex review

## 摘要

- **程式正確性**：glTF 匯入與短循環片段存在可由輸入觸發的 panic 路徑，PMX 貼圖也能在預算檢查前耗用大量記憶體。
- **AI 可用性**：多數動畫操作已有 schema 或 ACL 入口，但 `preview` 會漏掉部分資產相依錯誤，控制器模式下的 `seek` 也可能回報與實際姿勢不符的時間。
- **人工交接**：動畫資料、求值與 runtime 整合有清楚的模組邊界。`discover` 摘要已落後於實作，容易讓接手者漏用現有功能。
- **人機協作**：marker、stage 等編輯已有共用 ops 與 parity 測試。主要缺口在 revision 啟用時如何延續播放狀態，以及 runtime batch 的預檢是否與執行一致。

## Findings

### F1 [severity: high] [angle: code] [confidence: high] glTF 影像範圍可能在邊界檢查前溢位

- 位置: `crates/axiom-animation/src/import/gltf.rs:67`
- 問題: 影像 `bufferView` 的結束位置使用未檢查的整數加法。
- 證據: `b.get(view.offset()..view.offset() + view.length())` 先計算加法，再呼叫 `get`。目前鎖定的 glTF 依賴只檢查這兩個數值各自能否轉成 `usize`。
- 影響: 兩個欄位各自合法、相加卻溢位時，開啟溢位檢查的匯入程序會 panic，無法回傳 `invalid image buffer view`。
- 建議修正: 用 `checked_add` 計算結束位置，再檢查 slice 範圍。錯誤帶上 image 與 buffer view 的索引，並加入溢位回歸測試。

### F2 [severity: high] [angle: code] [confidence: high] PMX 先完整讀取貼圖，且缺少累計解碼預算

- 位置: `crates/axiom-animation/src/import/pmx.rs:193`、`crates/axiom-animation/src/import/pmx.rs:227`、`crates/axiom-animation/src/import/mod.rs:74`
- 問題: 單張貼圖的編碼大小上限檢查得太晚，PMX 路徑也沒有整份資產的貼圖解碼上限。
- 證據: PMX 接受最多 256 個貼圖路徑，使用 `std::fs::read(file)` 讀完整檔案，才進入 `texture` 的 32 MiB 檢查。每張不同路徑的解碼影像都保留在 `textures`。
- 影響: 一個 PMX 可在回傳大小錯誤前讀入超大檔案，也可用多張個別合規的貼圖耗盡程序記憶體。
- 建議修正: 共用有上限的讀取函式，最多讀取 32 MiB 加一 byte，並套用 glTF 與 AXRIG 已有的 256 MiB 累計解碼預算。錯誤帶上貼圖路徑。

### F3 [severity: high] [angle: code] [confidence: high] 短循環片段在 seek 後可讓 marker 掃描溢位

- 位置: `crates/axiom-runtime/src/animation.rs:1306`、`crates/axiom-runtime/src/animation.rs:1550`、`crates/axiom-animation/src/clip.rs:119`
- 問題: `seek` 保留原始秒數，marker 掃描把該時間換成 `u32` 圈數，再用未檢查的加法設定掃描上限。
- 證據: `p.time = a.seconds`，而 `crossings` 計算 `first = (prev.max(0.0) / duration).floor() as u32`，隨後求 `first + 8`。片段驗證允許任意短的正 duration。
- 影響: 對很短且有 marker 或 `on_end` 的循環片段 seek，再正向播放時，`first` 可飽和至 `u32::MAX`。開啟溢位檢查的固定步進會 panic。
- 建議修正: seek 時先將循環時間正規化，並以相對於本步起點的區間掃描圈數。保留每步圈數上限，加入短片段 seek 後繼續播放的回歸測試。

### F4 [severity: high] [angle: collab] [confidence: high] 刪除僅在 runtime 播放的片段會阻止有效 revision 啟用

- 位置: `crates/axiom-runtime/src/animation.rs:1157`、`crates/axiom-runtime/src/animation.rs:437`
- 問題: 熱重載沿用舊的 `active`，卻未確認新 revision 仍有該片段。
- 證據: 只要 `p.config.clip == previous.config.clip`，`transfer` 就複製 `previous.active`。接著 `p.evaluate(0.)?` 會對新 `clips` 查找該 ID，缺少時回傳 `clip not found` 並中止啟用。
- 影響: AI 用 `animation.play` 暫播片段後，人類或 AI 可提交一個合法移除該片段的 revision。編輯器與 `query` 會看到新 revision，runtime 仍停在上一版。
- 建議修正: 只有新 `clips` 仍含舊 `active` 時才延續播放。否則保留新 player 的作者設定，並一起重置時間和 marker 起點。

### F5 [severity: medium] [angle: ai] [confidence: high] `preview` 成功仍可提交無法啟用的動畫設定

- 位置: `crates/axiom-animation/src/authoring.rs:413`、`crates/axiom-runtime/src/animation.rs:223`、`crates/axiom-runtime/src/animation.rs:437`
- 問題: 動畫的 authoring 驗證檢查了 asset 與 controller 的引用，卻把 `animation.player.clip` 的解析留到 runtime 建立時。
- 證據: world validator 檢查 controller ID、transform、asset ID 與 retarget 引用。`Controller::new` 才將 `config.clip` 設成 `active` 並求值。CLI 的 `preview` 和 `apply` 共用前一階段的 world compile。
- 影響: `animation.player.clip` 拼錯時，AI 可先拿到成功的預覽，再以正確的 `expected_rev` 提交。live runtime 隨後拒絕啟用該 revision。
- 建議修正: 在有界的動畫預檢中，使用資產的片段索引驗證受影響的 player。讓 CLI `preview` 與提交前檢查共用這個驗證，並回傳指向 `animation.player/clip` 的診斷和可用片段 ID。

### F6 [severity: medium] [angle: collab] [confidence: high] 無效的 `inspect` 骨名可讓 runtime batch 部分生效

- 位置: `crates/axiom-runtime/src/animation.rs:1120`、`crates/axiom-runtime/src/animation.rs:516`
- 問題: `animation.inspect` 的 batch 預檢只驗證 entity，執行時才解析每個 bone ID。
- 證據: `check_command` 的 `inspect` 分支只檢查 `self.players.contains_key`，`Controller::inspect` 則對每個 `bones` 項目呼叫 `skeleton.bone(id)?`。
- 影響: `[play, inspect]` 可通過預檢，先開始播放，才因拼錯的骨名報錯。即使兩個命令之間沒有外部狀態變更，前一項仍已生效。
- 建議修正: 共用一個骨名解析函式，讓 `check_command` 在預檢時驗證所有骨名。加入 batch 後段骨名錯誤時前段不生效的測試。

### F7 [severity: medium] [angle: collab] [confidence: high] 同一片段的 `playing` 編輯會被舊 runtime 值覆蓋

- 位置: `crates/axiom-runtime/src/animation.rs:224`、`crates/axiom-runtime/src/animation.rs:1165`
- 問題: 同一 `clip` 的熱重載無條件沿用舊 `playing`，忽略作者對該欄位的修改。
- 證據: 建立 player 時以 `config.playing` 初始化，但 `transfer` 接著執行 `p.playing = previous.playing`。同一區塊中的 `speed` 與 `looping` 已各自比對新舊作者設定。
- 影響: 人類在 Inspector 或 AI 經 ACL 把 `playing` 改成 `false`，可成功提交並啟用新 revision，畫面卻繼續播放。
- 建議修正: 比照 `speed`，只有 `p.config.playing == previous.config.playing` 時才沿用 runtime 值。測試只修改 `playing` 的 revision 與 undo。

### F8 [severity: medium] [angle: code] [confidence: high] CPU skinning 在畫面擷取路徑逐幀重建完整頂點

- 位置: `crates/axiom-runtime/src/animation.rs:1210`、`crates/axiom-animation/src/skin.rs:27`
- 問題: 每次擷取畫面都同步重新 skin 所有啟用的 player，即使 pose 和 morph 權重沒有變動。
- 證據: `extract` 對每個 player 呼叫 `deform_with`。該函式配置 globals、三組骨矩陣或旋轉資料與完整頂點 `Vec`。結果再用新的 `Arc` 包裝。
- 影響: 暫停的角色和靜止的編輯器畫面仍持續在主執行緒配置緩衝並遍歷所有頂點。是否超過 16 ms 尚未量測。
- 建議修正: 以 pose 與 morph 權重的變更版本快取 skinned vertices，讓未變動的畫面重用結果，並讓 `deform_with` 接受可重用的骨矩陣暫存。

### F9 [severity: medium] [angle: collab] [confidence: high] 外部動畫依賴改了內容仍可能命中舊快取

- 位置: `crates/axiom-runtime/src/animation.rs:687`、`crates/axiom-runtime/src/animation.rs:708`、`crates/axiom-runtime/src/animation.rs:738`
- 問題: 快取只雜湊主檔內容，對相依檔只使用路徑、長度和修改時間。
- 證據: `asset_signature` 以 `std::fs::read(path)` 雜湊主檔。其他檔案記為 `(entry.path(), meta.len(), meta.modified().ok())`，快取命中就直接回傳舊的 `Arc<Asset>`。
- 影響: 人類替換外部 glTF buffer 或貼圖，若保留大小與修改時間，AI 重新載入後仍可能觀察到舊動畫資料。
- 建議修正: 由 importer 記錄實際讀取的相依檔，對這些檔案使用有界的串流內容雜湊，並讓熱重載沿用同一份相依清單。

### F10 [severity: medium] [angle: ai] [confidence: high] 控制器的 `seek` 回報新時間卻仍取樣舊姿勢

- 位置: `crates/axiom-runtime/src/animation.rs:1306`、`crates/axiom-runtime/src/animation.rs:355`、`crates/axiom-runtime/src/animation.rs:523`
- 問題: `seek` 接受 controller-driven player，但只改普通 player 的時鐘。
- 證據: `seek` 設定 `p.time`，未更新 `a.state`。有 controller 時，`blend_samples` 從 `a.compiled.samples(&a.state)` 取樣，`inspect` 頂層則回報 `self.time`。
- 影響: CLI 或 scenario 執行 `seek` 後可收到要求的秒數，查詢骨骼卻仍得到原有 controller phase 的姿勢。
- 建議修正: 先在 `seek` 分支明確拒絕 controller-driven player，並在 schema 說明適用範圍。若要支援 controller seek，再定義 state、layer 和 cross-fade 如何定位。

### F11 [severity: medium] [angle: collab] [confidence: high] 編輯器 scrub 只替換骨骼姿勢

- 位置: `crates/axiom-runtime/src/animation.rs:639`、`crates/axiom-runtime/src/animation.rs:679`、`crates/axiom-runtime/src/animation.rs:1218`
- 問題: scrub 產生預覽姿勢後，繪製仍使用 live player 的 morph 權重。
- 證據: `probe.evaluate(0.0)` 會求值 pose 與 morph，但 scrub 快取和交換只保留 `probe.pose`。`extract` 仍將 `p.morph_weights` 傳給 skinning。
- 影響: 人類拖動含臉部表情的片段時，骨骼顯示預覽時間的狀態，表情仍停在 live 狀態。人類看到的畫面和 AI 用相同時間驗證的結果可不同。
- 建議修正: scrub 快取同時保存 pose 與 morph 權重，擷取前成對交換，擷取後成對恢復。以現有 morph 動畫 fixture 加入回歸測試。

### F12 [severity: medium] [angle: code] [confidence: high] 斜向射線的膠囊距離可能使選取排序錯誤

- 位置: `crates/axiom-runtime/src/animation_parts.rs:354`、`crates/axiom-runtime/src/animation_parts.rs:415`、`crates/axiom-runtime/src/animation_parts.rs:492`
- 問題: `ray_capsule` 用軸線最近點當作固定球心，估算射線的進入距離。
- 證據: 求出 `gap` 後直接回傳 `t - sqrt(r² - gap²)`。斜射時，射線在進入膠囊側面的位置與軸線的最近點會跟著移動。現有測試涵蓋垂直側射及球體，未涵蓋斜射側面。
- 影響: `pick` 依這個距離比較候選件。兩個部位重疊時，CLI 查詢與畫面點擊都可能選中實際較遠的部位。
- 建議修正: 分別求有限圓柱側面與兩端球冠的交點，取最小有效距離。加入斜射與兩候選件排序測試。

### F13 [severity: medium] [angle: code] [confidence: high] `play` 指定的新速度會被上一段的 ramp 蓋過

- 位置: `crates/axiom-runtime/src/animation.rs:570`、`crates/axiom-runtime/src/animation.rs:911`
- 問題: `play` 設定新速度，但保留上一段播放的 `ramp`。
- 證據: `Controller::play` 寫入 `self.speed = a.speed`，未清除 `self.ramp`。下一個固定步進會依舊 ramp 的 `from`、`to` 和進度改寫 `p.speed`。
- 影響: `animation.play` 可當下回報要求的速度，下一步卻繼續上一段的速度變化，連帶改變新片段的 marker 與結束時機。
- 建議修正: 在共用的 `Controller::play` 清除 `self.ramp`，讓直接命令、stage 與 cue 使用同一行為。

### F14 [severity: low] [angle: ai] [confidence: high] `inspect` 的摘要及可見性錯誤會列出整份部位資料

- 位置: `crates/axiom-animation/src/authoring.rs:479`、`crates/axiom-runtime/src/animation.rs:531`、`crates/axiom-runtime/src/animation.rs:1107`、`crates/axiom-runtime/src/animation.rs:2123`
- 問題: schema 承諾省略 `bones` 時回傳摘要，實際仍附上全部 parts。可見性 selector 拼錯時也會列出完整名稱與群組。
- 證據: `animation.inspect` 一律呼叫 `old.inspect(&args.bones, true)`。`part_names` 將所有 material ID 和 group 串入錯誤字串，沒有項數或位元組上限。
- 影響: AI 查一個角色的播放摘要，或只拼錯一個 selector，都可能收到一大段與當次操作無關的資料。
- 建議修正: 為部位清單加明確投影選項，預設回傳計數。錯誤限制候選數與字串大小，並指出如何查完整清單。

### F15 [severity: low] [angle: human] [confidence: high] 動畫 `discover` 摘要漏掉已註冊的格式和操作

- 位置: `crates/axiom-animation/src/authoring.rs:289`、`crates/axiom-animation/src/authoring.rs:480`、`crates/axiom-animation/src/import/mod.rs:17`、`crates/axiom-runtime/src/animation_choreo.rs:225`
- 問題: `animation` 主題與同一功能的 schema、importer 和 action registry 各自維護，內容已不一致。
- 證據: topic 的格式清單缺 `.axrig`，controller 摘要只寫 clip 與 1D blend，action 清單缺 `stage` 和 `pick`。匯入分支、controller schema 與 runtime action 已實作這些功能。
- 影響: 接手者從 `discover animation` 查能力時，可能漏用現成的 Unity 匯入格式、2D blend 或舞台操作。
- 建議修正: 讓 topic 的 action 清單從已註冊的動畫 actions 產生，並用一個共用常數維護支援格式。更新 controller 摘要以包含 `blend2d`。
