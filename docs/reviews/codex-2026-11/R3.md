# R3 Rendering — Codex review

## 摘要

**一般程式碼**：合法相機設定可觸發 wgpu 驗證 panic。材質管線與舊版截圖會同步阻塞互動執行緒，CPU VFX 也有可從程式碼確認的重複配置。  
**AI 可用性**：CLI 能編寫與檢查多數渲染設定，但 `preview` 的驗證範圍小於實際啟用，部分視覺降級也缺少可直接查詢的指標。  
**人類接手**：主要渲染模組分工清楚，自訂 WGSL 的組裝仍依賴原始碼的字面拼法，讓一般重構可能悄悄改變畫面。  
**AI／人類協作**：材質來源、VFX 與後處理設定已有 GUI／ACL 共用操作與 parity 測試。主要落差在修訂提交後的啟用，以及非同步截圖與請求的配對。

## Findings

### F1 [severity: high] [angle: code] [confidence: high] 相機通過 authoring 驗證後仍可觸發 wgpu panic

- 位置: `crates/axiom-runtime/src/render.rs:947`、`crates/axiom-runtime/src/render.rs:1030`、`crates/axiom-runtime/src/postfx_gpu.rs:296`
- 問題: 世界、VFX 與體積後處理直接將正規化 viewport 乘上 framebuffer 尺寸。
- 證據: `Camera::validate` 允許 `x + w <= 1.00001`（`crates/axiom-core/src/ir.rs:594`）。`render.rs` 限制了 scissor 寬高，但 `set_viewport` 仍收到原始浮點寬高。專案使用的 wgpu 24 在 `x + width` 超出附件時拒絕該命令，未捕捉的驗證錯誤預設會 panic。
- 影響: `[0.5, 0.0, 0.500005, 1.0]` 可通過驗證並寫入 SQLite，視窗渲染該相機時卻可能終止。已儲存的修訂可在下次開啟時再次觸發。
- 建議修正: 共用一個 framebuffer 矩形轉換函式，先限制像素邊界，再以同一矩形計算投影、uniform、viewport 與 scissor。加入 authoring 容差及奇數尺寸的回歸測試。

### F2 [severity: high] [angle: collab] [confidence: high] Shader 預檢接受實際管線無法編譯的來源

- 位置: `crates/axiom-runtime/src/shader.rs:173`、`crates/axiom-runtime/src/shader.rs:403`、`crates/axiom-runtime/src/shader.rs:445`、`crates/axiom-runtime/src/shader_gpu.rs:323`
- 問題: authoring 驗證測試的是獨立探針，實際渲染編譯的是加入引擎宣告及入口點的另一份 WGSL。
- 證據: `validate_hook` 組裝 `{ABI}{hook}{vertex}{PROBE}`。GPU 另將 `scene.wgsl` 或 `mesh.wgsl`、表面 hook 與 wrapper 拼在一起。hook 可宣告與實際模板同名的 helper，例如 `scene_shadow`（`crates/axiom-runtime/src/shadow.wgsl:4`）。該名稱在探針中可用，在完整模組中會重複。`Store` 以 `World::compile` 驗證後提交，GPU 檢查發生在後續啟用。
- 影響: AI 或人類可提交一個已綁定材質的 shader 修訂。執行中的視窗保留舊 runtime 並回報啟用失敗，但下次以該修訂啟動視窗時，初始 `prepare_shaders` 的錯誤會退出事件迴圈。
- 建議修正: 讓 CPU 預檢共用 GPU 的 WGSL 組裝函式，以 Naga 驗證 cube 與 mesh 的實際入口點，並將組裝後行號映回使用者來源。加入保留名稱碰撞的 `preview` 回歸測試。

### F3 [severity: high] [angle: code] [confidence: high] 材質編譯在互動執行緒同步執行

- 位置: `crates/axiom-runtime/src/render.rs:556`、`crates/axiom-runtime/src/render.rs:619`、`crates/axiom-runtime/src/shader_gpu.rs:179`、`crates/axiom-runtime/src/shader_gpu.rs:256`
- 問題: CPU runtime 有背景啟用流程，材質快取未命中時仍會在採用新修訂的執行緒直接建立管線。
- 證據: `ShaderGpu::prepare` 遇到 cache miss 便呼叫 `self.compile`。每個來源建立 16 個管線變體，隨後以 `pollster::block_on(device.pop_error_scope())` 取回驗證結果。背景啟用完成後，`App` 仍在主執行緒呼叫 `renderer.prepare_shaders`（`crates/axiom-runtime/src/app.rs:2066`）。
- 影響: 編輯器採用含多個新材質的修訂時，必須等該批管線建立完成才能繼續處理畫面與輸入。這段工作沒有切分到 16 ms 預算內，實際耗時未量測。
- 建議修正: 讓材質 cache miss 進入單一有界的管線工作，按變體回報進度並處理取消與 watchdog。由同一工作序列管理 wgpu error scope，主執行緒只安裝仍對應最新修訂的完整結果。

### F4 [severity: high] [angle: code] [confidence: high] CPU VFX 每顆粒子都重新掃描並配置整張遮罩

- 位置: `crates/axiom-runtime/src/vfx.rs:162`、`crates/axiom-runtime/src/vfx.rs:311`、`crates/axiom-runtime/src/vfx.rs:496`
- 問題: 二值遮罩的有效像素清單在粒子求值中重建。
- 證據: `evaluate` 對 `texture_mask` 逐列掃描並 `collect::<Vec<_>>()`，再取 `pixels[index % pixels.len()]`。`extract` 為每顆 CPU 粒子呼叫 `evaluate`。
- 影響: 單一合法的 2,048 粒子、64×64 遮罩 emitter，每次擷取會掃描 8,388,608 個遮罩字元並建立 2,048 個暫存向量。這是從迴圈推得的工作量，未量測幀時間。
- 建議修正: 在 emitter 準備時一次建立有效像素表，讓畫面擷取與 `inspect` 共用。保留原先逐列順序以維持 seeded 結果。

### F5 [severity: medium] [angle: collab] [confidence: high] 截圖逾時後，舊 GPU 讀回可被交給新請求

- 位置: `crates/axiom-runtime/src/screenshot.rs:218`、`crates/axiom-runtime/src/screenshot.rs:243`、`crates/axiom-runtime/src/screenshot.rs:260`
- 問題: 讀回結果依當下的 `pending` 配對，缺少請求識別碼。
- 證據: `poll` 在 10 秒後取走 `pending`，`busy()` 隨即允許新請求。`grabbed` 直接以 `self.pending.take()` 取得收件人。呼叫端的 `GrabOwner::Loopback` 只保存裁切資訊，並在 `shots.poll()` 之後才嘗試取回舊讀回（`crates/axiom-runtime/src/app.rs:3104`、`:3132`）。
- 影響: 請求 A 已錄下畫面但讀回過慢，逾時後請求 B 進入。若 A 的讀回此時完成，A 的畫面與裁切範圍會寫到 B 的路徑，B 還會收到 `ok:true`。
- 建議修正: 為每次擷取分配單調遞增的 ID，經 `GrabOwner` 傳回 `grabbed`。丟棄已逾時 ID 的結果，並測試 A 逾時、B 排入、A 晚到的順序。

### F6 [severity: medium] [angle: collab] [confidence: high] 程序幾何的互斥條件直到 runtime 啟用才驗證

- 位置: `crates/axiom-runtime/src/geometry.rs:261`、`crates/axiom-runtime/src/geometry.rs:274`
- 問題: `render.geometry` 的 authoring 驗證只檢查元件本身，實體的所有權條件藏在 `geometry.prepare` factory。
- 證據: 元件註冊呼叫 `Geometry::validate()`，只檢查 shape、segments、rings 和 texture。factory 才要求有 transform、沒有 `render.mesh`，且沒有 `animation.player`，並回傳無實體路徑的 `procedural geometry requires one transform and exclusive mesh ownership`。
- 影響: 在已啟用 `geometry.prepare` 的世界，AI 可以把程序幾何加到現有 cube mesh，`preview` 與 `apply` 通過，執行中的編輯器卻只能保留舊 runtime。
- 建議修正: 將互斥條件抽成可共用的純驗證，在 authoring 階段對解析 prefab 後的元件執行，並回傳 `/entities/@ID/components/render.geometry` 及應移除或新增的元件。

### F7 [severity: medium] [angle: code] [confidence: high] 舊版編輯器截圖仍同步等待 GPU 並寫入 PNG

- 位置: `crates/axiom-runtime/src/render.rs:1158`、`crates/axiom-runtime/src/render.rs:1201`
- 問題: `Renderer::render` 的 `screenshot: Some` 分支會在呼叫執行緒完成整段 GPU 讀回與檔案寫入。
- 證據: 分支依序呼叫 `Maintain::Wait`、`rx.recv()`，複製像素、轉換 BGRA 並寫 PNG。`editor_view {capture}` 會設定 `pending_capture`，下一個可渲染幀將該路徑傳入同一分支（`crates/axiom-runtime/src/app.rs:1772`、`:3076`）。
- 影響: AI 使用舊版截圖入口時，互動視窗會等 GPU、PNG 壓縮與磁碟 I/O 完成。該等待路徑沒有 watchdog。
- 建議修正: 將 `editor_view {capture}` 接到既有的非同步讀回與 PNG 工作，並保留現有回覆欄位。同步擷取只留給一次性的 smoke runner。

### F8 [severity: medium] [angle: code] [confidence: high] 重複截圖路徑會直接截斷既有檔案

- 位置: `crates/axiom-runtime/src/screenshot.rs:125`、`crates/axiom-runtime/src/screenshot.rs:129`
- 問題: 截圖寫入缺少覆寫控制，PNG 編碼也直接寫入最終路徑。
- 證據: `write_crop` 使用 `File::create(path)`，接著才執行 `write_header` 與 `write_image_data`。建立檔案時就會截斷既有內容。
- 影響: AI 重試同一路徑，或挑到人類先前儲存的 PNG，會覆蓋原圖。若此時編碼或寫入失敗，原本可用的截圖也已遺失。
- 建議修正: 先在同目錄完成暫存 PNG，再以拒絕覆寫的方式發布到目的地。路徑已存在時回傳可更換檔名的診斷。

### F9 [severity: medium] [angle: code] [confidence: high] 每個實體掛載的 VFX 都重建整個世界的矩陣

- 位置: `crates/axiom-runtime/src/vfx.rs:387`、`crates/axiom-runtime/src/vfx.rs:409`、`crates/axiom-runtime/src/vfx.rs:483`
- 問題: 查詢單一掛載實體的世界座標會配置並計算全世界的矩陣。
- 證據: `origin` 在未使用有效 bone socket 時呼叫 `state.matrices()[slot]`。`matrices()` 建立一個完整 `Vec<Mat4>` 並走訪所有 transform（`crates/axiom-runtime/src/world.rs:76`、`:240`）。`step` 與 `extract` 都對每個 emitter 呼叫 `origin`，且 `step` 在檢查暫停前就已計算。
- 影響: 多個實體掛載 emitter 會在每個固定步與每次畫面擷取各自重算一遍世界矩陣。已暫停及非 ribbon emitter 也會在 `step` 支付這筆成本。
- 建議修正: `step` 只在未暫停的 ribbon 需要追加點時查詢位置。每次 `step` 或 `extract` 最多準備一份共享矩陣，供所有需要實體座標的 emitter 使用。

### F10 [severity: medium] [angle: code] [confidence: high] 後畫的天空會蓋住仍在裁切範圍內的遠處物件

- 位置: `crates/axiom-runtime/src/scene.wgsl:51`、`crates/axiom-runtime/src/render.rs:970`、`crates/axiom-runtime/src/render.rs:1439`
- 問題: authored sky 的深度略小於 far plane，且在不透明幾何之後繪製。
- 證據: `vs_sky` 輸出 `z=0.9999, w=1.0`，late sky 使用 `LessEqual`。深度落在 `(0.9999, 1.0)` 的不透明片段已通過相機裁切，天空仍會通過該像素的深度測試並寫入顏色。
- 影響: 相機切換到 authored sky 時，遠處物件可能提早消失，或在移動接近時重新出現。
- 建議修正: 將天空置於深度 `1.0`，並明確保留清除值給背景。加入一個深度介於 `0.9999` 與 `1.0` 的不透明物件測試。

### F11 [severity: medium] [angle: code] [confidence: high] 色差與熱扭曲會取樣到其他相機的畫面

- 位置: `crates/axiom-runtime/src/postfx.wgsl:13`、`crates/axiom-runtime/src/postfx.wgsl:31`、`crates/axiom-runtime/src/render.rs:1038`
- 問題: 體積後處理以各相機 viewport 繪製，但偏移取樣使用整張場景貼圖的範圍。
- 證據: WGSL 已收到 `s.viewport`，色差卻直接取樣 `uv + offset` 與 `uv - offset`，熱扭曲也只把座標限制到整張貼圖的 `[0,1]`。Rust 按相機順序在共用場景目標畫完該相機後立即執行後處理。
- 影響: 分割畫面接縫附近可混入前一個相機的顏色，或在尚未畫到另一個相機時取到黑色。同一效果會因相機順序而產生不同的邊界像素。
- 建議修正: 將每個色差與熱扭曲取樣限制在目前 viewport 內，並預留半個 texel 給線性過濾。以左右兩色的相機畫面驗證接縫。

### F12 [severity: medium] [angle: ai] [confidence: high] HDR 尚未就緒時，攜帶 `--screenshot` 的 smoke run 仍可成功輸出

- 位置: `crates/axiom-runtime/src/render.rs:579`、`crates/axiom-runtime/src/render.rs:608`、`crates/axiom-runtime/src/render.rs:1201`、`crates/axiom-runtime/src/hdr_build.rs:227`
- 問題: 最終擷取等待後處理管線，但等待結束時仍有缺項，就會繼續擷取 fallback 畫面。
- 證據: `post` 初始為預設值，只有 `post_need(...).is_empty()` 才採用請求設定。建置逾時時 `PostBuild::update` 設定 `State::Failed` 並回傳 `Step::Nothing`，渲染接著輸出 PNG，函式仍可回傳 `Ok(true)`。
- 影響: 只檢查程序成功與 PNG 存在的 AI smoke 腳本，會把缺少 HDR、bloom 或 FXAA 的畫面當成指定設定的驗證結果。
- 建議修正: 當 smoke 擷取要求的後處理仍未就緒時，回傳包含建置狀態與原因的結構化錯誤，並略過該次 PNG 寫入。

### F13 [severity: medium] [angle: ai] [confidence: high] Ribbon 接受尺寸曲線與顏色漸層，畫面卻固定使用基礎值

- 位置: `crates/axiom-runtime/src/vfx.rs:138`、`crates/axiom-runtime/src/vfx.rs:454`、`crates/axiom-runtime/src/vfx.rs:487`、`crates/axiom-runtime/src/vfx_gpu.rs:409`
- 問題: 通用 VFX 編輯與檢查路徑支援 ribbon 實際繪製時沒有讀取的欄位。
- 證據: 驗證接受 ribbon 的 `size_curve` 與 `color_gradient`。`inspect` 用 `evaluate` 產生含曲線尺寸的 CPU 粒子樣本。實際 ribbon 卻只取 `e.size`、`e.color`，GPU 頂點準備只沿 trail 調整 alpha。
- 影響: AI 或人類提交曲線後，修訂與 `inspect` 都可呈現新值，ribbon 畫面維持原樣，導致兩方對同一修訂得到不同結論。
- 建議修正: 在 schema 與 `inspect` 標示各 renderer 實際使用的欄位，並讓 GUI 與 ACL 共用同一條曲線適用性檢查。既有 ribbon 資料可先回報相容性診斷。

### F14 [severity: low] [angle: ai] [confidence: high] 被擠出 GPU 預算的 VFX 燈光沒有觀測指標

- 位置: `crates/axiom-runtime/src/lighting.rs:398`、`crates/axiom-runtime/src/lighting.rs:437`、`crates/axiom-runtime/src/render.rs:662`
- 問題: 燈光封裝計算了丟棄數量，但 renderer 沒有保存或公開該值。
- 證據: `authored_locals.chain(vfx)` 只填前 32 個 GPU 槽位，`PackedLighting` 記錄 `dropped: total - local_count`。渲染只把有效燈光與數量寫入 uniform，`dropped` 在 runtime 中僅由單元測試讀取。
- 影響: 人類新增場景燈光後，AI 的 VFX emitter 仍可在 `inspect` 顯示運作，但其燈光可能已被擠掉。單靠 `observe_delta` 無法確認原因。
- 建議修正: 將最後呈現幀的 `local_count`、`dropped` 與容量放入精簡的 `metrics.lighting`，供 `observe_delta` 投影。

### F15 [severity: low] [angle: human] [confidence: high] WGSL 格式調整可讓 `vertex_offset` 悄悄失效

- 位置: `crates/axiom-runtime/src/shader.rs:445`、`crates/axiom-runtime/src/scene.wgsl:7`、`crates/axiom-runtime/src/mesh.wgsl:14`
- 問題: 色彩管線的頂點 hook 靠整行字串替換注入，沒有檢查替換是否命中。
- 證據: `fragment` 用 `template.contains("@vertex fn vs_main")` 區分模板，再對兩種不同拼法的 `let world` 運算式呼叫 `replace`。原始模板本身是合法 WGSL，替換零次時仍可編譯。
- 影響: 新維護者只調整 `mesh.wgsl` 中 `let world` 那行的空白，就可能讓程序變形在 mesh 上消失，而 cube 仍顯示正確。
- 建議修正: 使用明確的注入標記並檢查恰好命中一次。加一個組裝測試，確認 cube 與 mesh 的實際頂點入口都呼叫 `vertex_offset`。
