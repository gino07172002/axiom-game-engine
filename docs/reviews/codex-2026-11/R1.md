# R1 Authoring core and protocol — Codex review

## 摘要

- **程式正確性**：三條輸入路徑可觸發 panic，讓原本應回傳診斷的請求中斷。部分檔案大小限制在完整讀取後才生效。
- **AI 可用性**：`discover`、`preview` 和 `observe_delta` 提供完整工作流的入口，但 schema、投影回應及 `verify --ticks` 有可誤導自動化判斷的落差。
- **人類交接**：IR、操作與儲存層的分工清楚。手寫的 schema 清單與請求型別已出現差異，修改協定時需要同步維護多處。
- **AI 與人類共編**：一般提交的 `expected_rev` 在交易內檢查。提案重新套用、預覽寫鎖及大量編輯的 GUI／ACL 行為仍有落差。

## Findings

### F1 [severity: high] [angle: code] [confidence: high] 缺少 `audio.spatial` 時，音源驗證會 panic

- 位置: `crates/axiom-core/src/audio.rs:666`、`crates/axiom-core/src/ir.rs:295`
- 問題: 世界有 `audio.source`、沒有 `audio.listener`，且缺少 `audio.spatial` 時，驗證無法回傳原本準備好的 `invalid_audio`。
- 證據: 驗證使用 `.first().map(...).unwrap_or((listeners[0].0, "audio.listener"))`。`unwrap_or` 會先求值預設參數，因此即使已有音源，仍會索引空的 `listeners`。
- 影響: 用 `preview` 驗證手寫音源，或用 `apply` 移除這類世界的 `audio.spatial`，會中斷請求。`serve` 的逐行錯誤處理只處理 `Result`。
- 建議修正: 改用 `.or_else(|| listeners.first().map(...))` 選擇診斷對象，並加入只有音源且未排程音訊系統的回歸測試。

### F2 [severity: high] [angle: code] [confidence: high] 相機跟隨的 `NaN` 距離下界會在驗證前觸發 panic

- 位置: `crates/axiom-core/src/acl.rs:1705`、`crates/axiom-core/src/ops.rs:901`
- 問題: ACL 接受非有限浮點值，而共用操作在檢查範圍前就可能用該值呼叫 `clamp`。
- 證據: ACL 將 `min` 直接解析為 `f32`。省略 `distance` 時，`add_camera_follow` 執行 `follow.distance.clamp(follow.min_distance, ...)`，之後才呼叫 `follow.validate()`。
- 影響: 有效的相機選取與目標搭配 `min=NaN` 時，`preview` 或 `--propose` 也會因 `clamp` 的下界檢查而 panic。
- 建議修正: 在共用操作內先檢查 `min_distance`、`max_distance` 為有限值且順序正確，再推導預設距離。錯誤回傳對應欄位的 `invalid_value`。

### F3 [severity: high] [angle: code] [confidence: high] 驗證接受的資源陣列可讓後續共用編輯操作 panic

- 位置: `crates/axiom-core/src/audio.rs:384`、`crates/axiom-core/src/registry.rs:198`、`crates/axiom-core/src/ops.rs:1896`、`crates/axiom-core/src/ops.rs:1963`、`crates/axiom-core/src/ops.rs:1788`
- 問題: 資源驗證接受 Serde 的序列表示，後續操作卻假設儲存的 JSON 一定是物件。
- 證據: `AudioLibrary` 的欄位都有 `#[serde(default)]`，經 `serde_json::from_value` 可將 `[]` 解成空資料庫。音訊片段操作仍對原始 JSON 執行 `.as_object_mut().and_then(...).expect(...)`。自動補上互動按鍵也對 `input.bindings` 採同樣做法。
- 影響: 一個通過驗證並已儲存的空音訊資源，可在下次新增片段時中斷 ACL 或編輯器操作。再次開啟資料庫仍會讀到相同的資源表示。
- 建議修正: 寫入時保留既有物件的 JSON，對已成功解碼的序列表示先轉回物件，再以可回傳 `Diagnostic` 的方式修改欄位。測試應涵蓋已儲存的序列表示。

### F4 [severity: medium] [angle: collab] [confidence: high] `preview` 在整批驗證期間占用 SQLite 寫交易

- 位置: `crates/axiom-core/src/store.rs:65`、`crates/axiom-core/src/store.rs:231`、`crates/axiom-core/src/store.rs:280`、`crates/axiom-core/src/store.rs:563`
- 問題: 預覽只需要一致的讀取快照，卻與提交共用 `TransactionBehavior::Immediate`。
- 證據: `Preview` 呼叫 `edit(..., false)`，仍會先取得寫交易，再解碼、套用、編譯前後兩份世界及計算差異。`commit` 只控制最後是否寫入。連線的 `busy_timeout` 為 3 秒。
- 影響: AI 預覽大型批次期間，另一條連線上的人類提交必須等待寫鎖。等待逾時會回 SQLite 鎖定錯誤，無法由 `revision_conflict` 得知應重讀哪個版本。
- 建議修正: `preview` 使用 deferred 讀交易，或先讀取一致的 `(rev, world)` 快照再離線驗證。實際提交保留寫交易與交易內 CAS。

### F5 [severity: medium] [angle: code] [confidence: high] 編輯器更新仍可同步解碼整份外部提交的世界

- 位置: `crates/axiom-core/src/store.rs:174`、`crates/axiom-core/src/store.rs:186`、`crates/axiom-core/src/store.rs:605`
- 問題: `current_shared` 的快取未命中時，同步讀取並解碼完整 revision。`Verify` 也同步讀取和編譯整份世界。
- 證據: `current_shared` 找不到相同 `rev` 就呼叫 `current()`，後者查詢整個 `world` 欄位並反序列化。編輯器的更新輪詢直接呼叫此方法，Verify 動作也直接呼叫 `Store::execute(Request::Verify {})`。呼叫端分別位於 `crates/axiom-runtime/src/app.rs:1906`、`:2474`。
- 影響: 獨立 CLI 程序提交的 revision 不在編輯器的程序內快取。編輯器首次採用該版本時，整份讀取與解碼會占用更新迴圈。這些路徑沒有 16 ms 的工作量上限，實際耗時未量測。
- 建議修正: 主執行緒只做 revision 探測和已解碼快取查詢。快取未命中的讀取、解碼與 Verify 交給有界背景工作，完成時帶回結果對應的 `rev`。

### F6 [severity: medium] [angle: code] [confidence: high] `set_where` 對每個命中物件往返轉換整份 World IR

- 位置: `crates/axiom-core/src/protocol.rs:365`、`crates/axiom-core/src/local.rs:121`、`crates/axiom-core/src/local.rs:248`、`crates/axiom-core/src/acl.rs:2550`
- 問題: 批次欄位更新的成本隨「命中數 × 世界大小」成長。
- 證據: `SetWhere` 最多逐一呼叫 4,096 次 `target.edit`。每次先做 `json!(world)`，改一處，再用 `serde_json::from_value(doc)` 重建整份世界。ACL 先在 `scratch` 執行一次，之後預覽或提交時再執行一次。
- 影響: 一個語法簡短且符合上限的大範圍 `set`，可在同一筆操作中重複配置與轉換數千份世界資料，並延長提交寫鎖的持有時間。
- 建議修正: 將定位及欄位修改抽成可操作同一份文件的函式。每個 `SetWhere` 只轉換一次世界，保留 prefab 覆寫行為及整批原子驗證。

### F7 [severity: medium] [angle: code] [confidence: high] 套件的 `manifest.json` 略過根目錄邊界檢查

- 位置: `crates/axiom-core/src/package.rs:404`、`crates/axiom-core/src/package.rs:414`、`crates/axiom-core/src/package.rs:424`
- 問題: 驗證套件目錄位於邊界內，無法限制其 `manifest.json` 連結指向何處。
- 證據: manifest 直接以 `std::fs::read(root.join("manifest.json"))` 讀取。世界檔和宣告資產則先做 `canonicalize()`，並檢查解析後路徑仍以套件根目錄開頭。
- 影響: 在解包結果保留符號連結的環境中，載入器可讀取套件目錄外的 manifest，將外部檔案當成套件設定解析。
- 建議修正: 讓 manifest 使用與世界檔相同的 canonical 路徑邊界檢查，並確認它是一般檔案。加入解析後路徑越界的測試。

### F8 [severity: medium] [angle: code] [confidence: high] CLI 與套件檔案的大小限制在配置記憶體後才檢查

- 位置: `crates/axiom-cli/src/lib.rs:609`、`crates/axiom-cli/src/lib.rs:797`、`crates/axiom-cli/src/lib.rs:858`、`crates/axiom-core/src/package.rs:414`、`crates/axiom-core/src/package.rs:429`
- 問題: 多個檔案輸入路徑把整份檔案讀進記憶體後才套用上限。
- 證據: `rpc FILE` 和 `apply`／`preview FILE` 先 `read_to_string`，再交給 `parse_request` 檢查 1 MiB。`scenario`、manifest 和套件世界也先完整讀取，再檢查各自上限。CLI 的相應 stdin 路徑已有 `take(limit + 1)`。
- 影響: 超大檔案可先造成大量配置，CLI 有可能在印出可復原的超限訊息前耗盡記憶體。
- 建議修正: 用 `File::open` 搭配 `take(limit + 1)` 共用有界讀取，再依各格式的既有上限回傳錯誤。較大的匯入格式也應設定自己的上限。

### F9 [severity: medium] [angle: collab] [confidence: high] `verify --ticks` 的驗證與模擬可能使用不同 revision

- 位置: `crates/axiom-cli/src/lib.rs:830`、`crates/axiom-cli/src/lib.rs:841`、`crates/axiom-core/src/store.rs:605`
- 問題: CLI 組合的驗證結果沒有固定在同一份世界快照。
- 證據: CLI 先執行 `Request::Verify`，由 Store 讀取當前世界並填入外層 `rev`。模擬前 CLI 又呼叫 `current()`，用這次讀到的 `(rev, w)` 建立 `WorldRuntime`。`--measure` 也在驗證之後另外讀取資料庫。
- 影響: 若人類在兩次讀取之間提交，AI 可收到外層 `rev=N`，以及對 `N+1` 執行的模擬結果，進而把模擬通過歸給錯誤的版本。
- 建議修正: CLI 在本機驗證開始時取得一次快照，驗證和模擬都接收該快照。量測若保留重讀資料庫的設計，每次取樣都應限制在同一個 revision 或在版本變更時作廢。

### F10 [severity: medium] [angle: collab] [confidence: high] `resolve --rebase` 可把提案套到審查時未命中的物件

- 位置: `crates/axiom-core/src/store.rs:371`、`crates/axiom-core/src/store.rs:466`、`crates/axiom-core/src/store.rs:490`、`crates/axiom-core/src/protocol.rs:365`
- 問題: 提案保存原始編輯，重新套用時會在最新世界重新解譯其中的選取條件。
- 證據: `Propose` 儲存序列化的 `edits` 及基準版本的預覽差異。`rebase` 改用最新 `rev`，把同一批原始 `edits` 直接交給 `edit_in`。`SetWhere` 每次執行都會重新呼叫 `matches`。
- 影響: 一筆修改某個 tag 下所有實體的提案，能在重新套用時一併改到提案送出後才新增該 tag 的實體。審查者看到的原預覽沒有這些變更。
- 建議修正: 過期提案含 `SetWhere` 時，將核准導向現有的 `conflicts` 加 `keep` 三方合併流程。若確實要用最新世界重新選取，先產生新預覽並以該 `rev` 核准。

### F11 [severity: medium] [angle: collab] [confidence: high] 大量欄位更新的 GUI 與 ACL 使用不同批次上限

- 位置: `crates/axiom-core/src/ops_world.rs:1015`、`crates/axiom-core/src/acl.rs:2382`、`crates/axiom-core/src/protocol.rs:365`、`crates/axiom-core/src/store.rs:262`
- 問題: 共用的逐物件欄位語意，在兩個入口有不同的批次表示。
- 證據: `ops::set_fields` 每個物件、每個欄位產生一筆 `SetField`，Store 上限是 256 筆。ACL `set` 只產生一筆 `SetWhere`，最多可命中 4,096 個物件。Inspector 的多選貼上使用前者，見 `crates/axiom-runtime/src/editor/mod.rs:1107`。
- 影響: 對 257 個具相同元件的實體貼上同一份元件，GUI 批次會被拒絕，等價的 ACL `set` 可以在一個 revision 完成。
- 建議修正: 讓兩個入口都使用同一個可承載穩定目標 ID 的批次欄位操作，共用命中數上限。用 256 與 257 個目標補 parity 測試。

### F12 [severity: medium] [angle: collab] [confidence: high] 並行提交提案可越過 256 筆待審上限

- 位置: `crates/axiom-core/src/store.rs:361`、`crates/axiom-core/src/store.rs:372`
- 問題: 待審筆數的檢查與新增分屬不同 SQL 陳述，兩者沒有共同的寫交易。
- 證據: `Propose` 完成 `self.edit(..., false)` 後，先 `SELECT COUNT(*)`，再獨立 `INSERT`。預覽交易已在 `edit` 返回時結束。
- 影響: 待審數為 255 時，兩條連線都可讀到 255 並各自成功新增，留下 257 筆待審提案。
- 建議修正: 在短寫交易中重查待審數並插入，或改用單一條件式 `INSERT`，根據影響列數回覆佇列已滿。

### F13 [severity: medium] [angle: ai] [confidence: high] `observe_delta` 靜默略過找不到的投影路徑

- 位置: `crates/axiom-core/src/observe.rs:75`、`crates/axiom-core/src/observe.rs:90`、`crates/axiom-core/src/observe.rs:134`
- 問題: 呼叫端無法從成功回應區分路徑拼錯和該欄位目前未提供。
- 證據: 投影只在 `raw.pointer(field)` 回傳 `Some` 時插入欄位。找不到的路徑沒有診斷或清單，相同的空投影可再回傳 `unchanged: true`。
- 影響: AI 若把 `/requested_rev` 拼錯，可能持續輪詢空投影，卻無法知道應修正欄位名稱。
- 建議修正: 對明確指定的 `fields` 回傳有界的 `missing_fields`，並區分無效的 JSON Pointer 與此次觀察沒有該值。測試應同時涵蓋拼錯與合法的可選欄位。

### F14 [severity: low] [angle: human] [confidence: high] `set_where` 的手寫 schema 和實際請求型別不一致

- 位置: `crates/axiom-core/src/discovery.rs:33`、`crates/axiom-core/src/registry.rs:708`、`crates/axiom-core/src/protocol.rs:353`
- 問題: 維護者需同步修改編輯列舉、編輯種類清單和選取 schema，目前三者已出現落差。
- 證據: `schema edits` 的 `kinds` 漏列 `set_where`。`discover local` 將 `set_where.select` 指向讀取用的 `selection`，其 `limit` 上限為 128，且允許 `cursor` 和 `fields`。實際編輯上限為 4,096，並拒絕游標及非空欄位投影。
- 影響: 依 schema 建立的客戶端可能拒絕合法的 `limit: 256`，或在本機接受伺服器會拒絕的帶游標編輯。
- 建議修正: 為讀取與修改定義各自的選取 schema，讓上限和驗證共用常數。加入 `set_where` 的探索項目，並用契約測試對照宣告與實際接受的請求。

### F15 [severity: low] [angle: ai] [confidence: high] 含中文的 ACL 腳本可因自動產生的提案備註而被拒絕

- 位置: `crates/axiom-core/src/acl.rs:2567`、`crates/axiom-core/src/store.rs:366`
- 問題: ACL 依字元數截短備註，Store 依 UTF-8 位元組數限制備註。
- 證據: ACL 用 `text.trim().chars().take(2048).collect()` 產生備註，Store 要求 `note.len() <= 2048`。備註來自原腳本，因此包含解析時跳過的註解。
- 影響: 一行有效編輯加上較長的中文註解可正常預覽，卻在 `--propose` 時收到 `proposal note exceeds 2 KiB`。該入口沒有獨立的備註參數可修正。
- 建議修正: 以共用的 2,048 位元組常數，在 UTF-8 字元邊界截短自動備註，並以繁體中文腳本加入測試。
